# Обмен Autexa ↔ 1С: пилот

## Что реализовано и что ещё требуется

В Autexa есть изолированное подключение для одного автосервиса и филиала,
ключ обмена, выключенные по умолчанию направления, журнал, сопоставление
идентификаторов, проверка версий и защита от повторной обработки событий.
Настройки находятся в вебе: **Настройки компании → 1С**, в приложении:
**Интеграции → 1С**. Ключ показывается один раз и не хранится в клиентском кэше.

`bridge.mjs` — готовый транспорт между API Autexa и HTTP-адаптером конкретной
информационной базы 1С. Это **не готовое расширение .cfe/.epf для УНФ**.
В репозитории пока нет проверенного адаптера метаданных и проведения документов
УНФ. Без него синхронизация с 1С не заработает. Нельзя включать пилот на рабочей
базе, выдавать его за универсальную интеграцию или обещать поддержку любой 1С.

Начальный целевой профиль — **1С:Управление нашей фирмой 3**. Конкретный релиз,
доработки базы, организации, склады, договоры, кассы, счета, способы оплаты,
единицы измерения и правила проведения должен подтвердить специалист 1С.
На 2026-10-03 тестовой базы у владельца нет; проверены программные контракты
и аварийные сценарии, но не обмен с работающей 1С.

Платформа 1С предоставляет [REST/OData](https://v8.1c.ru/platforma/rest-interfeys/)
и [средства интеграции](https://v8.1c.ru/platforma/integraciya/). Это транспортные
возможности платформы; они не задают единый состав документов всех конфигураций.

## Запуск транспорта

Node.js 20+; дополнительные npm-пакеты не нужны. Запускать рядом с сервером
1С, с одним процессом на подключение. Публиковать базу 1С в открытый интернет
не требуется: локальный адаптер может слушать loopback. При удалённом адаптере
обязателен HTTPS. Перенаправления HTTP запрещены, секреты в URL запрещены.

1. Создать подключение в Autexa, выбрать филиал и сохранить ключ в менеджере
   секретов. Подключение остаётся приостановленным.
2. Специалист реализует и проверяет адаптер по контракту ниже. Его `/health`
   не должен возвращать `ready: true` до проверки сопоставлений на копии базы.
3. Скопировать `config.example.json` в `config.local.json`, указать адреса,
   **код подключения из Autexa**, нужные типы данных и отдельный `stateDir`.
4. Передать `AUTEXA_ONE_C_KEY` и `ONE_C_ADAPTER_KEY` окружению процесса через
   используемый менеджер секретов. Не записывать ключи в конфиг, git или логи.
5. После сверки разрешить направления в настройках Autexa, подтвердить проверку
   сопоставлений и включить обмен. В конфиге транспорта перечислить только
   включённые типы; адаптер объявляет разрешённые направления отдельно.
6. Сначала `node bridge.mjs config.local.json --once`, сверить оба журнала,
   затем `node bridge.mjs config.local.json` под менеджером процессов.

Остановка SIGTERM/SIGINT завершает текущий цикл, сохраняет состояние и снимает
блокировку. После аварийного завершения `bridge.lock` остаётся: перед удалением
проверить записанный PID и отсутствие работающего процесса. Повторный экземпляр
с тем же каталогом не запускается. `state.json` нельзя очищать для исправления
ошибки: он содержит версии и отложенные подтверждения. Сохраняйте каталог вместе
с резервной копией настроек адаптера. Смена подключения требует нового каталога.

## Контракт HTTP-адаптера 1С, версия 1

Все ответы — JSON. Авторизация — отдельный `Authorization: Bearer …`.
Адаптер должен ограничить пользователя одной базой/организацией/складом,
запретить доступ к остальным объектам и не писать ключи или полные тела в логи.
Максимум 100 записей в странице, ответ не больше 8 MiB, таймаут 30 секунд.
Ответы 401/403/429/5xx не считаются успешными подтверждениями.

### GET /health

```json
{
  "protocol": 1,
  "configuration": "UNF3",
  "connectionId": "код подключения Autexa",
  "ready": true,
  "durableIdempotency": true,
  "exportEntities": ["products", "clients"],
  "importEntities": ["products", "clients"]
}
```

`exportEntities` означает **из 1С в Autexa**, `importEntities` — **из Autexa в 1С**.
Возможные типы: `products`, `stock`, `clients`, `purchases`, `workOrders`,
`payments`. Типы документов и обязательные реквизиты соответствуют версии
конкретного адаптера; не включать неподдержанные типы.

### GET /changes?limit=100&cursor=…

Устойчивая очередь изменений, курсор непрозрачный. Порядок учитывает зависимости:
сначала справочники и сопоставления, затем документы. Событие неизменно после
создания; исправленный документ получает новый `eventId`. Очередь переживает
перезапуск 1С. Отсутствие объекта в странице **не означает удаление**.

```json
{
  "items": [
    {
      "eventId": "устойчивый идентификатор события",
      "entityType": "products",
      "externalId": "UUID объекта 1С",
      "baseRevision": "последняя известная версия объекта Autexa, если есть",
      "payload": { "name": "Баллон", "barcode": "B-01" }
    }
  ],
  "nextCursor": "позиция последнего события",
  "hasMore": false
}
```

`nextCursor` сохраняется и для последней страницы. Пустая последняя страница может вернуть прежний курсор или
`null`, сохраняя прежнюю позицию. `hasMore: true` требует нового курсора.
`payload` должен соблюдать allowlist и бизнес-контракт backend one-c; это не
произвольный JSON документа 1С. Персональные данные сотрудников не передаются.

### POST /changes/ack

```json
{ "eventId": "…", "status": "applied", "autexaId": "…", "receiptId": "…" }
```

Ответ `{"accepted":true}`. Допустимы `applied`, `needs_review`, `rejected`.
Последние два статуса сохраняются в журнале сверки адаптера и не обозначают
успешное проведение. Повторное подтверждение идемпотентно. Нельзя создавать
новый eventId, чтобы автоматически обойти `needs_review` после неизвестного
исхода записи в Autexa: сначала сверить документ.

### POST /apply

```json
{
  "eventId": "SHA256 перехода: подключение, тип, id, версия и предыдущая подтверждённая версия 1С",
  "entityType": "products",
  "autexaId": "…",
  "externalId": null,
  "revision": "версия Autexa",
  "baseExternalRevision": "последняя известная версия 1С, если есть",
  "payload": { "name": "Баллон", "article": "B-01" }
}
```

Адаптер должен **в одной транзакции** проверить/создать запись inbox по
`(connectionId,eventId)`, сопоставление и бизнес-изменение. Повтор того же события
возвращает сохранённый результат, другое тело с тем же ключом — 409.
Потеря HTTP-ответа не должна создавать второй платёж или повторное движение.
При несовпадении `baseExternalRevision` — `needs_review`, без перезаписи.
Не искать документы по одному названию, сумме или артикулу вместо стабильного ID.

Успех: `{"status":"applied","externalId":"UUID 1С","externalRevision":"версия 1С"}`.
Конфликт: `{"status":"needs_review"}`. Отказ: `{"status":"rejected"}`.
Успех допустим только после коммита. Созданные документы проходят штатные
проверки конфигурации. Прямая запись регистров остатков/кассы недопустима.
Изменение, применённое из Autexa, не должно порождать бесконечный обратный обмен:
адаптер сохраняет исходную версию и источник изменения в своём регистре.

## Проверки перед реальным подключением

`node --test integrations/one-c/bridge.test.mjs` проверяет транспорт, в том числе
потерю ответов, перезапуск, сохранение подтверждений и изоляцию каталогов.
Backend-тесты отдельно проверяют области доступа и обработку событий.

На копии **реальной** конфигурации необходимы двусторонние сценарии: создание и
изменение карточек, дробные количества/копейки, закупка и приход, заказ-наряд и
оплата, две одновременные правки, повтор событий, обрыв после коммита, раздельные
филиалы, пауза и замена ключа. Закрытые документы, возвраты, неподдержанные
проводки и неоднозначные сопоставления должны останавливаться на сверку.

Пока эта проверка и конфигурационный адаптер отсутствуют, пункт «полноценная
синхронизация с 1С» остаётся незавершённым. Остальные исправления приложения
можно выпускать независимо: обмен изначально выключен.
