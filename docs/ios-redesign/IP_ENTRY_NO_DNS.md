# Четвёртый рубеж кольца: вход по IP, которому не нужен DNS

**Дата:** 26.07.2026
**Задача владельца:** «хочу чтобы приложение работало и с ВПН, и без»
**Затронуто:** `mobile/app.json` (`extra.apiFallbackUrls`), `mobile/src/api/__tests__/apiRingConfig.test.ts` (новый), прод-сервер (nginx, certbot, cron)

## Проблема

Кольцо хостов перебирает **имена**: `autexa.pw` → `autexa-cloud.ru` → Яндекс-шлюз. Когда у клиента ломается не путь до конкретного домена, а само разрешение имён (VPN-клиент с перехватом DNS, фильтрация оператора), все три рубежа умирают одновременно. Механизм пойман живьём в этот же день — см. [DNS_BLOCKED_DIAGNOSIS.md](DNS_BLOCKED_DIAGNOSIS.md): внутри устройства даже Safari не открывал `autexa.pw`, тогда как тот же сервер по IP отвечал.

Раньше вывод был «нужен нативный сетевой модуль, чтобы держать SNI при обращении по адресу». Он оказался неверен: с **15 января 2026 Let's Encrypt выдаёт сертификаты на IP-адреса** (обязательно профилем `shortlived`, 160 часов), и с марта 2026 это умеет Certbot. Значит вход по адресу можно сделать полностью валидным по TLS — без единой строки нативного кода, одинаково на iOS, Android и вебе.

## Решение

Четвёртый, последний элемент кольца: `https://212.8.229.254/api`. Обычный трафик по-прежнему идёт по именам; адрес включается только когда имена не отвечают, потому что стоит в списке последним и селектор кольца принимает первый здоровый хост.

### Сервер

| Что                     | Как                                                                                                                                                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Клиент ACME             | Certbot **5.7.0** в `/opt/certbot` (venv). Пакетный 2.9 из apt IP-адрес отвергает на своей же проверке. Пакет намеренно НЕ удалён — его systemd-юниты служат расписанием                                                                                                 |
| Выпуск                  | `certbot certonly --webroot --webroot-path /var/www/acme --ip-address 212.8.229.254 --cert-name autexa-ip --preferred-profile shortlived`                                                                                                                                |
| Почему webroot          | IP-адреса поддерживают только плагины `webroot`, `manual`, `standalone`. **Плагин nginx их не умеет**, standalone занял бы 80-й порт                                                                                                                                     |
| nginx                   | `/etc/nginx/sites-available/autexa-ip`: блок `listen 80` отдаёт только `/.well-known/acme-challenge/` (для ACME), блок `listen 443 ssl default_server` — сам вход                                                                                                        |
| Почему `default_server` | **SNI не может содержать IP-адрес** (RFC 6066), клиент, идущий на адрес, не присылает имя вовсе — и nginx отдаёт ему сертификат сервера по умолчанию. Без `default_server` отдавался чужой `autexa-cloud.ru`, и проверка сертификата падала                              |
| Host для upstream       | Задан константой `autexa.pw`, а не `$host`: upstream обязан видеть тот же vhost, что и при обращении по домену                                                                                                                                                           |
| Продление               | `renew_hook = systemctl reload nginx` в renewal-конфиге + глобальный `/etc/letsencrypt/renewal-hooks/deploy/00-reload-nginx.sh`. Таймер `certbot.timer` (00:00 и 12:00 UTC) переведён на venv-клиент через drop-in `/etc/systemd/system/certbot.service.d/override.conf` |
| Сторож                  | `/opt/zr-auto-pro/scripts/check-ip-entry.sh`, cron каждые 6 часов (`/etc/cron.d/autexa-ip-entry`), лог `/var/log/autexa-ip-entry.log`                                                                                                                                    |

### Почему сторож самолечащийся, а не оповещающий

Сертификат живёт 160 часов, а каналов алертов на сервере нет ни одного (`SENTRY_DSN` в серверном `.env` пуст). Молча сгнивший резерв хуже отсутствующего: о нём узнают в тот момент, когда он нужен. Поэтому скрипт не жалуется, а пытается починить — продлевает и перезагружает nginx сам; проверка здоровья идёт **с валидацией сертификата**, чтобы просроченный считался поломкой, как его и увидит приложение.

## Проверено

Сервер:

- `https://212.8.229.254/api/health` → **200**, `ssl_verify_result: 0` (сертификат доверенный), тело `{"status":"ok"}`;
- в сертификате `X509v3 Subject Alternative Name: critical, IP Address:212.8.229.254`, издатель Let's Encrypt YE2, срок 26.07 → 02.08;
- регрессия: `autexa.pw`, `www.autexa.pw`, `autexa-cloud.ru` → 200 с доверенным TLS, сайт → 200;
- `certbot renew --dry-run` → «Simulating renewal … for 212.8.229.254» + «all simulated renewals succeeded» по всем трём сертификатам;
- сторож при первом запуске: `ok: здоров, сертификат ещё 6 дн.`

Приложение (симулятор iPhone 17 Pro, iOS 26.4.1, **VPN включён — DNS внутри устройства мёртв, Safari не открывает домены**):

- вход с заведомо неверным паролем вернул **401 «Неверный телефон или пароль»** — авторитетный ответ бэкенда, то есть запрос дошёл;
- в хранилище приложения `active_api_base_v1 = https://212.8.229.254/api` — кольцо само выбрало адресный вход;
- 623 теста, 33 сьюта зелёные; `typecheck`, `lint` чисто.

## Границы

- Если VPN режет **сам IP** сервера, а не только DNS, не поможет ничто на стороне приложения. В проверенном случае адрес через VPN проходил.
- Сертификат на IP короткоживущий по политике LE — это не наш выбор и изменить нельзя. Отсюда обязательность сторожа.
- IP-адрес VDS зашит в конфиг приложения. **При смене хостинга или IP этот элемент кольца обязан обновиться вместе с сервером**, иначе он превращается в мёртвый рубеж. Страж конфига — `apiRingConfig.test.ts`.

## Приёмка владельцем

1. Включи VPN, из-за которого раньше не работало, и войди в приложение — должно войти как обычно.
2. Выключи VPN — тоже должно работать (обычный путь по домену).
3. **Баг** — если при VPN снова «Сервер недоступен» или «Нет подключения к интернету».
