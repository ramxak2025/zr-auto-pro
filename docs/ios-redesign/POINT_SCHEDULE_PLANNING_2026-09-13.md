# Филиал у графика, плана постоянных расходов и записей (2026-09-13)

Серверная часть — миграция `167_schedule_planning_bookings_point.sql`,
`backend/src/schedule/`, `backend/src/planning/`, `backend/src/bookings/`,
`backend/src/points/points.service.ts` (привязка истории). Продолжение
`POINT_SESSION_LOGIN_2026-09-11.md` и `POINT_INSTANT_SWITCH_MOBILE_2026-09-11.md`.

## Проблема / motivation

Жалоба владельца (2026-09-13, дословно):

> «после последних правок перестала работать расписание! невозможно отметить
> нормально кто пришел кто опоздал… и еще когда переключаюсь между филиалами
> почему-то данные с основной точки там! а это отдельные автосервисы!!! почему
> расписание с другого филиала там или постоянные расходы и так далее»

Два независимых корня.

### 1. Отметка «пришёл / опоздал» падала на сервере

`ScheduleService.ensureShiftOpen` (появился в 3.7.0) открывал смену по отметке в
графике и вычислял её филиал агрегатом `MIN(tp.id)` по назначениям сотрудника.
Колонка `tenant_points.id` — `uuid`, а агрегатов `min`/`max` для `uuid` в
PostgreSQL 16 **не существует**: `ERROR: function min(uuid) does not exist`
(воспроизведено на живом PostgreSQL 16.14). Последствия:

- строка графика уже была записана (`UPDATE`/`INSERT … ON CONFLICT` шли до
  открытия смены и вне транзакции), затем запрос падал с 500;
- приложение откатывало оптимистичную отметку и показывало «Не удалось
  сохранить», а при следующем обновлении отметка появлялась — то самое
  «невозможно отметить нормально»;
- смена по отметке не открывалась вовсе: человек на работе, а «кто сейчас на
  смене» и карточка филиала показывали ноль.

### 2. График, план постоянки и записи не имели своего филиала

Волна 161 дала филиал денежным строкам (чеки, расходы, смены, зарплата, касса),
а три раздела выразила «составом команды» — назначениями `user_points`:

- **График** (`schedule_entries`): строка дня филиала не имела. Сетка филиала =
  сетка назначенных на него сотрудников. Но по безопасному дефолту 156
  сотрудник **без назначений виден везде**, и у тенанта, который людей по
  филиалам ещё не расставил (ситуация владельца), оба автосервиса показывали
  один и тот же график — отметка, поставленная в филиале, появлялась и в
  основном сервисе.
- **Постоянные расходы** (`fixed_costs`, экран «Постоянные расходы» в
  планировании): конфиг тенанта, один на всю сеть. Аренда филиала вычиталась из
  accrual-прибыли основного сервиса и наоборот; на экране филиала лежал план
  основного.
- **Записи** (`bookings`): филиал резолвился через назначения мастера, запись
  без мастера была видна везде.

## Архитектура решения

Правило одно и то же, что у денег: **у строки есть свой `point_id`, он
штампуется филиалом сессии (163) в момент записи и режется строгим равенством**
(`common/point-scope.pointFilterSql`). Состав команды (`user_points`) остаётся
для того, для чего был: кто виден в сетке и в пикерах. Чей день, чей план и чья
запись — говорит сама строка.

### Миграция 167

- `point_id UUID REFERENCES tenant_points(id) ON DELETE SET NULL` у
  `schedule_entries`, `fixed_costs`, `bookings` (`ADD COLUMN IF NOT EXISTS`).
- Функция `autexa_point_by_live_assignment(tenant, user)` — филиал, если
  сотрудник назначен ровно на один **живой** филиал, иначе NULL. Через
  `array_agg(...)[1]`, а не `min(uuid)`.
- Привязка истории у тенантов с живой основной точкой (`is_main`), только
  `point_id IS NULL`:
  - график — единственное живое назначение сотрудника → основной сервис;
  - записи — филиал своего чека (проведённые) → живое назначение мастера →
    основной;
  - план — основному (до 167 он был один на тенант).
- Та же лестница добавлена в `PointsService.HISTORY_ATTACH_SQL`: тенант,
  которому первый филиал заведут после прогона миграции, получит привязку тем
  же путём (тест `points-history-attribution` сверяет список таблиц).
- Индексы `(tenant_id, point_id, date)` / `(tenant_id, point_id, scheduled_at)`
  / `(tenant_id, point_id)`.
- У тенантов без филиалов не меняется ничего: `point_id` остаётся NULL, фильтр
  не применяется, поведение байт-в-байт прежнее.

### График (`ScheduleService`)

| Метод             | Что изменилось                                                                                                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getAll`          | Строки — `se.point_id = филиал сессии` (строгое равенство). Состав строк сетки клиент берёт списком `GET /users?scope=point`.                                                                                                           |
| `getToday`        | Состав — по назначениям (дефолт 156 сохранён); день графика и открытая смена присоединяются только этого филиала. Мастер, стоящий сегодня в графике филиала Б, в филиале А показывается «без графика, не на смене».                     |
| `create`          | Штампует `point_id` филиалом сессии. Уникальный индекс `(tenant_id, user_id, date)` — один день на сотрудника во всей сети, поэтому запись дня из филиала Б, когда он стоял в А, **переносит** день в Б («последняя правка побеждает»). |
| `update`          | Гейт записи `assertRowPointForWrite('schedule_entries', …)`: день чужого филиала — 404 «Запись не найдена».                                                                                                                             |
| `remove`          | Тот же гейт (фильтр по филиалу в `DELETE`).                                                                                                                                                                                             |
| `applyWorkMode`   | «Все мастера» = команда этого филиала; каждый день штампуется филиалом сессии; дни, стоявшие в другом филиале, переезжают (см. `create`).                                                                                               |
| `ensureShiftOpen` | Филиал смены = филиал строки графика, параметром. Никаких агрегатов.                                                                                                                                                                    |
| `getMyStats`      | Не менялся: личная статистика сотрудника — по всей сети (как и его личный дашборд зарплаты).                                                                                                                                            |

**Почему перенос, а не отказ.** После привязки истории все дни лежат в основном
сервисе. Если бы запись дня из филиала отвечала 409, владелец не смог бы
расставить график филиала, не удаляя дни по одному в основном. Перенос — та же
семантика, что у этого upsert внутри одного филиала всегда была. Оборотная
сторона честно названа в acceptance ниже (пункт 6).

### Производные срезы графика

- `SalaryService.workedShiftsByUser(…, pointId)` — «ЗП за смену» в филиале
  делит начисления филиала на смены, отработанные в нём же. Личный дашборд
  сотрудника (`getMy`) по-прежнему без фильтра — он весь по сети.
- `EmployeesService` — дисциплина, серия без опозданий, сводка смен, рейтинг
  дисциплины по команде: дни графика только филиала карточки.
- `ReportsService.computeAlerts` — «опоздавшие сегодня» только своего филиала.

### План постоянных расходов (`PlanningService`)

- `fixed_costs`: список / создание / правка / удаление — по филиалу сессии,
  правка и удаление за гейтом `assertRowPointForWrite('fixed_costs', …)`.
- `employee_compensation` (оклады) остаётся конфигом **сотрудника** (одна строка
  на человека), в срез филиала попадают оклады его **команды** (`user_points`,
  дефолт 156). Пикер сотрудников на экранах планирования — `?scope=point`.
- `ReportsService.computeDashboardV2`: accrual-прибыль филиала вычитает **его**
  план и оклады **его** команды. Раньше — весь план сети; комментарий
  «честное ограничение» из 161 снят.

### Записи (`BookingsService`)

- Список — `b.point_id = филиал сессии`; старый предикат по назначениям
  мастера удалён.
- Создание штампует филиал сессии; правка и отмена — за гейтом
  `assertRowPointForWrite('bookings', …)`. `convert` (привязка чека при
  сохранении заказ-наряда) гейта не имеет: запись считается выполненной, где бы
  ни пробили чек.
- Проверка пересечений по мастеру (`findConflict`) осталась по всей сети:
  человек не может быть в двух местах.

### Клиенты (`mobile/`, `frontend/`)

- `hooks/useUsers.ts`: `usePointUsers()` / `USERS_POINT_QUERY_KEY = ['users',
'point']` — команда текущего филиала. Ключ под префиксом `['users']`, поэтому
  инвалидации справочника сотрудников дёргают и его; `persistentCache` зеркалит
  его отдельным слотом (ключ хранения — полный query key). Справочник
  «Сотрудники» и назначение людей на филиалы остаются на неограниченном
  `['users']` — иначе нельзя назначить на филиал того, кто на нём ещё не
  работает.
- `ScheduleScreen` (сетка / рейтинг / настройки) и `PlanningScreen` (пикер
  окладов) — на `usePointUsers()`; оптимистичная перестановка мастеров правит
  слот `['users','point']`.
- `PlanningScreen` — подпись автосервиса (`PointIndicator`, только показ).
- Web: `SchedulePage` и `PlanningPage` — `usersApi.getAll({ scope: 'point' })`
  под ключом `['users','point']`. Индикатор филиала в вебе уже в `Layout`.
- `shared/types`: `ScheduleEntry.pointId`, `FixedCost.pointId`,
  `Booking.pointId` — опциональные, только для чтения; клиент их не отправляет.
- Версия приложения 3.7.2.

## Fallback-стратегия

- **Одноточечный тенант.** `point_id` остаётся NULL, ни один фильтр не
  применяется, `?scope=point` отдаёт всех: поведение байт-в-байт прежнее.
- **Сотрудники не расставлены по филиалам** (дефолт 156). Все видны в сетке
  каждого филиала; дни у каждого сотрудника — там, где их поставили. После
  миграции вся история — в основном сервисе; график филиала владелец
  расставляет в филиале (дни переезжают). Чтобы в сетке филиала были только его
  люди — назначить их в карточке сотрудника («Филиалы сотрудника») или в
  разделе «Филиалы».
- **Старые сборки (3.7.0/3.7.1)** работают без изменений контракта: новые поля
  ответов опциональны, список сотрудников без `?scope=point` по-прежнему
  отдаёт всех (сетка покажет всех, но дни — только своего филиала).
- **Android** — общий TS-код, iOS-only API не используются, native-модули не
  тронуты, `expo prebuild` не требуется.

## Acceptance criteria (проверка владельцем)

1. **Отметка прихода.** Расписание → тап по ячейке сегодняшнего дня → «Смена» /
   «Опоздал <1ч» / «Опоздал >1ч». Ячейка окрашивается сразу и **не
   откатывается**, баннера «Не удалось сохранить» нет. Вкладка «Сегодня»
   показывает сотрудника «на смене».
2. **График по филиалам.** В основном сервисе поставить смену мастеру на завтра.
   «Ещё → Филиалы → Перейти» в филиал → Расписание: этого дня в сетке **нет**.
   Поставить в филиале смену другому мастеру → вернуться в основной: её там нет.
3. **Постоянные расходы по филиалам.** В филиале «Ещё → Планирование /
   Постоянные расходы»: список пуст (история ушла основному сервису), сверху
   подпись автосервиса. Добавить «Аренда ТопГаз» → в основном сервисе её нет, а
   на главной филиала «Чистая прибыль по начислению» уменьшилась ровно на её
   амортизацию.
4. **Записи.** Запись, созданная в филиале, видна только в его списке.
5. **Состав сетки.** Пока сотрудники не назначены на филиалы — в сетке каждого
   филиала все мастера (это ожидаемо). Назначить мастера только на филиал
   (карточка сотрудника → «Филиалы сотрудника») → в основном сервисе его строка
   из сетки исчезает.
6. **Перенос дня (известное поведение, не баг).** Если у мастера день стоит в
   основном сервисе, а администратор филиала ставит ему статус на тот же день —
   день переезжает в филиал вместе с новым статусом; в основном сервисе он
   пропадает. Это возможно только для сотрудников, видимых в обоих филиалах
   (не назначенных никуда). Лечится назначением сотрудников.

**Багом считается:** откат отметки с баннером ошибки; день или план,
поставленный в одном автосервисе и видимый в другом; пустая сетка «Нет
мастеров» у тенанта без филиалов; исчезновение истории графика у тенанта без
филиалов.
