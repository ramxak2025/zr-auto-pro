# Зарплата: выплата без подтверждения мастером (миграция 158)

Дата: 2026-09-10. Затронуто: backend `salary/`, `shared/`, mobile «Зарплата», web `SalaryPage`.

## Проблема (со слов владельца)

1. «Блок где сумма указана уродски обрезана снизу и сверху» — поле суммы в формах выдачи/штрафа/премии.
2. «Убери подтверждение выплат мастером» — владелец выдал ЗП, а деньги фиксировались только после нажатия
   мастером «Принять». Мастера кнопку игнорировали: касса деньги отдала, а расхода в книгах нет, «Выплачено»
   не растёт, остаток не уменьшается — владелец выдаёт повторно.
3. «Очень неудобно её выдавать, листать» — карточка сотрудника на ~2000 строк и список с полосой «Выдать»
   под каждой строкой.

## Решение

### (а) Поле суммы

Денежные поля приведены к эталону «Расходов» (`ExpensesScreen.amountInputWrapper` / `amountInput`):
₽ слева, кегль `fontSize['2xl']`, **реальный вертикальный паддинг** вместо `padding: 0`. Именно нулевой
паддинг на iOS резал глифы: высота однострочного `TextInput` считается по кеглю без запаса. Высота нигде
не зафиксирована — при системном увеличенном шрифте поле растёт, а не обрезает цифры. Многострочные
(комментарий/причина) переведены на `paddingVertical` по той же причине.

`heroAmount` карточки: 34/44 вместо 38/46 — запас строки к кеглю ×1.29, цифры не режутся при крупном шрифте.

### (б) Подтверждение → «просмотрено»

Новая модель:

| Было                                             | Стало                                                             |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| `createPayout` → `status='pending'`, расхода нет | `createPayout` → `status='accepted'` + расход в ТОЙ ЖЕ транзакции |
| мастер «Принять» → расход                        | мастер видит уведомление, «Понятно» → `viewed_at`                 |
| мастер «Отклонить» → `rejected`                  | отклонения нет; ошибочную выплату отменяет владелец               |
| владелец видит «Принято / Ожидает»               | владелец видит «Выдано» + «Просмотрено / Не просмотрено»          |

Расход создаётся **ровно один раз** — в транзакции выдачи; отмена (`cancelPayout`) сторнирует его прежней
логикой для `accepted`. Штрафы подтверждения никогда не имели — модель совпадает без правок.

Миграция `158_salary_payout_viewed.sql`: колонка `viewed_at TIMESTAMPTZ` + бэкфилл (`accepted`, у которых
`decided_at > created_at`, то есть решение принималось отдельной транзакцией старого flow → мастер выплату
видел). Индекс `idx_salary_payouts_unviewed` — частичный, по непросмотренным.

### Что со старыми `pending` — намеренно НЕ трогаем

У них нет зеркального расхода. Пометить `accepted` без расхода = потерять деньги в кассе; создать расход
миграцией = выдумать движение денег, которого владелец не подтверждал (мог выписать ошибочно). Обе ветки —
тихая правка чужой бухгалтерии, поэтому решение принимает владелец:

- `POST /salary/payouts/:id/settle` — зафиксировать (создаст расход, аудит `salary_payout_settle`);
- `POST /salary/payouts/:id/cancel` — отменить.

В UI такая строка помечена «Не зафиксирована» + подсказка «Расход не записан — зафиксируйте или отмените»;
в меню ⋯ мобилки и кнопкой «Зафиксировать» в вебе. Новые `pending` не создаются никогда.

### Fallback для старых клиентов

`POST /salary/payouts/:id/decide` **оставлена живой**. Для зафиксированной (или отменённой) выплаты она
трактуется как «просмотрено» и отвечает 200 — приложение старой версии с кнопками «Принять/Отклонить»
закрывает уведомление штатно, ошибки не показывает, деньги не двигает. Для оставшихся легаси-`pending`
прежнее поведение accept/reject сохранено 1:1.

Пуш мастеру при выдаче остался, текст без «подтвердите»: «Зарплата выдана · Сумма: N ₽»,
`data.type='payout-issued'` (листенер `SalaryNotificationContext` матчит по нему).

### (в) Компактнее

- Список: «Выдать» — компактный чип **под суммой прямо в ряду** (была полноширинная полоса, −28 pt на строку);
  `paddingVertical` 12→10, `minHeight` 68→60.
- Карточка: «Штраф» и «Премия» в один ряд; «Премии», «Прошлые выплаты», «Штрафы» — раскрывающиеся секции
  (по умолчанию свёрнуты); ужаты отступы hero / totals / секций / строк.
- Форма выдачи помещается на один экран: комментарий спрятан за ссылкой «+ Комментарий».
- Позиция в списке при смене месяца сохраняется: у запроса `['salary', from, to]` есть
  `placeholderData: prev => prev`, `keyExtractor` стабилен по `masterId` — FlashList не перемонтируется.

## Acceptance criteria (проверка на устройстве)

1. «Зарплата» → «Выдать» у сотрудника: поле суммы — крупные цифры, ничего не обрезано; в тёмной теме тоже;
   Настройки → Экран → Размер текста «максимум» — цифры по-прежнему целые.
2. Выдать сумму → сразу: у сотрудника в списке «Выплачено» выросло, «К выплате» уменьшилось; в «Расходах»
   появилась строка «Зарплата: <имя>»; в «Движении денег» деньги ушли.
3. На устройстве мастера — уведомление «Зарплата выдана» с одной кнопкой «Понятно». Кнопок «Принять» и
   «Отклонить» нет.
4. У владельца в карточке сотрудника строка выплаты: «Выдано» + «Не просмотрено»; после того как мастер
   нажал «Понятно» — «Просмотрено».
5. ⋯ → «Отменить выплату» у выданной: расход исчезает из «Расходов», сумма возвращается в «К выплате».
6. Если в базе остались выплаты старого формата — они помечены «Не зафиксирована»; ⋯ → «Зафиксировать»
   создаёт расход ровно один раз (повтор отвечает «Выплата уже зафиксирована»).
7. Баг: любая ситуация, где после одной выдачи в «Расходах» появилось две строки или ни одной.
