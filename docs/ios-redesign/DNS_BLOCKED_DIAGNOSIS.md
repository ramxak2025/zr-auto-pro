# Третий сетевой диагноз: «имена не разрешаются» вместо ложного «нет интернета»

**Дата:** 26.07.2026
**Затронуто:** `mobile/src/utils/networkDiagnosis.ts` (новый), `mobile/src/components/OfflineBanner.tsx`, `mobile/src/screens/LoginScreen.tsx`, `mobile/src/utils/__tests__/networkDiagnosis.test.ts` (новый)
**Платформы:** iOS + Android (общий код, ничего платформо-специфичного)

## Проблема

Владелец рецидивом сообщал «иногда с ВПН не работает», а приложение показывало красное «Нет подключения к интернету» и модалку «Сервер недоступен». Оба сообщения указывали не туда: искали поломку в приложении и на сервере, тогда как сервер был жив.

Механизм впервые пойман живьём 26.07.2026 в iOS-симуляторе на машине владельца (VPN-клиент **Happ**, интерфейс `utun10`, через него же уходил и подменный диапазон `198.18.0.0/15`):

| Проверка                                                                 | Результат                                                       |
| ------------------------------------------------------------------------ | --------------------------------------------------------------- |
| `autexa.pw/api/health` с хоста                                           | 200                                                             |
| `autexa-cloud.ru/api/health` с хоста                                     | 200                                                             |
| Яндекс-шлюз `/api/health` с хоста                                        | 200                                                             |
| Нейтральная проба `clients3.google.com/generate_204` с хоста             | 204                                                             |
| Safari **внутри устройства** → `autexa.pw`                               | «не удаётся найти сервер»                                       |
| Safari внутри устройства → `https://212.8.229.254` (тот же сервер по IP) | дошёл; TLS поднялся, только предупреждение о несовпадении имени |

Вывод: маршрут и TLS живы, ломается **разрешение имён**.

**Почему кольцо хостов здесь бессильно.** Кольцо перебирает ИМЕНА (`autexa.pw` → `autexa-cloud.ru` → Яндекс-шлюз). При мёртвом DNS все три умирают одновременно; нейтральные пробы (`ya.ru`, `captive.apple.com`, `gstatic`) — тоже, потому что они тоже по именам. Диагноз «нет интернета» формально следовал из проб, но по сути был ложным.

## Решение

Третья ступень пробы — достижимость по **IP-литералу**, которой DNS не нужен. DoH-эндпоинты Cloudflare и Google доступны по адресу, и их сертификаты валидны на сам IP, поэтому TLS проходит без имени:

- `https://1.1.1.1/dns-query?name=autexa.pw&type=A` (`accept: application/dns-json`)
- `https://8.8.8.8/resolve?name=autexa.pw&type=A`

Успехом считается любой разобранный DoH-ответ с числовым полем `Status` — даже отрицательный ответ доказывает, что пакеты ходят. Порядок ступеней экономный: имена спрашиваем первыми, и при их успехе вторая ступень не запускается вовсе.

Вердикт `ConnectivityVerdict`:

| Вердикт       | Условие                        | Что показываем                                                                          |
| ------------- | ------------------------------ | --------------------------------------------------------------------------------------- |
| `internet-ok` | прошла любая проба по имени    | «Сервер недоступен в вашей сети — попробуйте Wi-Fi или VPN» (оранжевый)                 |
| `dns-blocked` | имена мертвы, IP-литерал дошёл | «Не разрешаются адреса — мешает VPN или DNS. Выключите VPN» (оранжевый, иконка глобуса) |
| `no-internet` | не прошло ничего               | «Нет подключения к интернету» (красный)                                                 |

`LoginScreen` использует тот же вердикт (бюджет 3 с на ступень) и вместо «Сервер недоступен» показывает «Мешает VPN или DNS» с конкретным действием.

## Fallback-стратегия

Диагноз ставится **только по положительному доказательству**. Если IP-проба тоже молчит — а в РФ «жёсткие окна» операторов режут и Cloudflare, и Google — возвращается прежний вердикт `no-internet`, то есть поведение до этой правки. Никакой регрессии в сетях, где новая проба недоступна.

Ограничение честно: это **диагностика, а не обход**.

**ОБНОВЛЕНО в тот же день:** обход всё-таки найден и внедрён — см. [IP_ENTRY_NO_DNS.md](IP_ENTRY_NO_DNS.md). Первоначальный вывод «нужен нативный модуль, потому что `fetch`/`axios` не держат SNI при обращении по адресу» оказался неверным: Let's Encrypt с января 2026 выдаёт сертификаты на IP-адреса, поэтому четвёртым элементом кольца стал `https://212.8.229.254/api` — полностью валидный по TLS вход, которому DNS не нужен. Диагноз ниже сохраняет смысл как честное сообщение на случай, когда не работает и адресный вход (например, если VPN режет сам IP).

## Проверки

- `npx jest src/utils/__tests__/networkDiagnosis.test.ts` — 9 тестов: экономия второй ступени, captive-portal HTML со статусом 200 не считается ни интернетом, ни DoH-ответом, отрицательный DoH всё равно доказывает сеть, отменённый signal, потолок по таймауту, IP-литералы в адресах проб.
- Полный прогон: `npm run typecheck`, `npm run lint`, `npx jest` — 617 тестов, 32 сьюта, зелёные.
- **Живая проверка на симуляторе** (iPhone 17 Pro, iOS 26.4.1, VPN Happ включён — то есть в реальных условиях отказа): баннер показал «Не разрешаются адреса — мешает VPN или DNS. Выключите VPN», модалка — «Мешает VPN или DNS. Сеть работает, но адрес сервера не удаётся разрешить». Значит DoH-проба по IP реально дошла сквозь тот же VPN, который убил DNS.

## Приёмка владельцем

1. Включи VPN, который ломает связь, и попробуй войти.
2. Ожидается: оранжевая полоса «Не разрешаются адреса — мешает VPN или DNS. Выключите VPN» и модалка с тем же смыслом. **Баг** — если снова показано красное «Нет подключения к интернету» или «Сервер недоступен».
3. Выключи VPN, нажми «Проверить» — полоса должна исчезнуть.
4. В обычной сети без VPN ничего измениться не должно: полосы нет, вход как раньше.
