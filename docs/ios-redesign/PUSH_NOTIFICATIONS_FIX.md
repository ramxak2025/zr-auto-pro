# Уведомления: почему их не было и как починено (Round 14, зона 5)

Дата: 2026-08-03. Ветка: `feat/round14-batch`.
Жалоба владельца: «нативных уведомлений нет, почини и чтобы гибко настраивать».

---

## 1. Проблема

Пуши не приходили **ни одному** пользователю iOS из TestFlight/App Store. При этом:

- сервер логировал `Expo push response status: 200`;
- ни одной ошибки ни в логах, ни в Sentry;
- на dev-сборке всё «работало».

То есть система выглядела полностью здоровой и одновременно не доставляла ничего.

---

## 2. Корень

`mobile/app.json` объявлял плагин так:

```json
["expo-notifications", { "icon": "./assets/icon.png", "color": "#2563eb" }]
```

Без `mode`. А сам плагин (`node_modules/expo-notifications/plugin/build/withNotificationsIOS.js`):

```js
const withNotificationsIOS = (config, { mode = 'development', ... }) => {
  config = withEntitlementsPlist(config, (config) => {
    if (!config.modResults['aps-environment']) {
      config.modResults['aps-environment'] = mode;   // ← 'development'
    }
```

Результат — **проверено на сгенерированном артефакте** `mobile/ios/Autexa/Autexa.entitlements`:

```xml
<key>aps-environment</key>
<string>development</string>
```

Дальше цепочка, которая делает баг невидимым:

1. Приложение с этим entitlement регистрируется в **sandbox** APNs и получает sandbox-токен.
2. Expo отправляет push в **production** APNs.
3. Production APNs отвечает `BadDeviceToken`.
4. Expo возвращает **ticket** `status: "ok"` — тикет означает только «принято в очередь».
5. Реальный отказ виден **исключительно в delivery receipt**, а receipts бэкенд никогда не читал.
6. `logger.error` в Sentry не уходил: `backend/src/common/sentry.ts` инициализируется с `integrations: []`.

Итог: сборка была зарегистрирована в одной сети APNs, а доставка шла в другую, и ни один слой не мог об этом сообщить.

### Побочный корень, найденный там же

В `Info.plist` **отсутствовал ключ `UIBackgroundModes`**. Значит, тихие data-пуши
(`sendDataToTenant`, `_contentAvailable: true`), которыми бэкенд инвалидирует кеш между
устройствами, тоже никогда не будили приложение.

---

## 3. Решение

### 3.1 `mobile/app.config.js` (новый файл)

`mode` не может быть константой: **development**-подписанная сборка обязана иметь
`aps-environment: development` (dev-профиль просто не несёт значения `production`, codesign
упадёт). Поэтому значение вычисляется:

| Условие                                       | `aps-environment` |
| --------------------------------------------- | ----------------- |
| `APS_ENV=development` или `production`        | как указано       |
| `EAS_BUILD_PROFILE === 'development'`         | `development`     |
| всё остальное (включая отсутствие переменных) | **`production`**  |

Дефолт `production` выбран сознательно: если пломба переменных когда-нибудь сломается,
отказ будет **громким** (локальная dev-сборка не подпишется), а не тихим (пользователи
месяцами без уведомлений — ровно то, что произошло).

`mobile/eas.json` → профиль `development` получил `"env": { "APS_ENV": "development" }`.

Дополнительно включён `enableBackgroundRemoteNotifications: true` → в `Info.plist`
появляется `UIBackgroundModes: [remote-notification]`.

Разрешённое значение продублировано в `extra.apsEnvironment`, поэтому его видно и без Xcode:

```bash
npx expo config --type prebuild | grep -i apsEnvironment
```

и оно показывается в экране «Уведомления» → блок «Диагностика».

**Проверено после `expo prebuild --platform ios --clean`:**

```xml
<key>aps-environment</key><string>production</string>
<key>UIBackgroundModes</key><array><string>remote-notification</string></array>
```

> **Грабли.** Плагин пишет entitlement только если ключа ещё нет
> (`if (!config.modResults['aps-environment'])`). Прогон `expo prebuild` **без `--clean`**
> поверх существующей `mobile/ios/` сохранит старое значение. Всегда `--clean`.
> На EAS это неважно: `mobile/ios/` в `.gitignore`, сборщик генерирует проект с нуля.

### 3.2 Видимость доставки (backend/src/push/push.service.ts)

- `postToExpo` теперь **возвращает** результат (`ExpoSendOutcome`), а не `void`.
- Принятые тикеты через 15 с проверяются через `/--/api/v2/push/getReceipts`
  (`scheduleReceiptSweep`, таймер `unref`'нут — не держит graceful shutdown).
- Ошибки квитанций логируются и уходят в Sentry через `Sentry.captureMessage`
  (обходя `integrations: []`), `DeviceNotRegistered` — прунит токен.
- В запросы к `exp.host` добавляется `Authorization: Bearer ${EXPO_ACCESS_TOKEN}`,
  если переменная задана. Без этого включение «Enhanced Security for Push» в аккаунте
  Expo мгновенно положило бы всю доставку. Переменная добавлена в `.env.example`.

### 3.3 Регистрация токена перестала врать

`upsertToken` при срабатывании anti-hijack-гарда (`rowCount === 0`) возвращал 200, и клиент
считал себя подписанным навсегда. Теперь возвращается `{ registered: false, reason }`, клиент
это логирует, а экран диагностики показывает «Устройство зарегистрировано: Нет».

### 3.4 Android

Ранний `return` для Android заменён на проверку реального конфига
(`isAndroidPushConfigured()` → `android.googleServicesFile`). Код готов; **пуши на Android
физически невозможны, пока владелец не заведёт Firebase-проект** — см. §5.

## 4. Гибкие настройки

### Миграция `151_notification_settings.sql`

`notification_settings(user_id PK, master_enabled, sound, quiet_from, quiet_to,
tz_offset_minutes, updated_at)`. Отсутствие строки == все дефолты включены, поэтому
**бэкфилла нет и никто не теряет уведомления от самого факта деплоя**.

RLS не включается — таблица без `tenant_id`, тот же класс, что `notification_mutes` и
`push_tokens`, намеренно исключённые в миграции 112.

### Категории

`NotificationCategory` расширен с 5 до 11. Шесть пушей, которые слались **вообще без
тумблера**, переведены с `sendToUser` на `sendToUserCategory`:

| Событие                     | Категория          | Файл                          |
| --------------------------- | ------------------ | ----------------------------- |
| Машина готова к выдаче      | `order_ready`      | `checks.service.ts`           |
| Оплачено — можно выдавать   | `order_paid`       | `checks.service.ts`           |
| Напоминание о записи        | `booking_reminder` | `booking-reminder.service.ts` |
| Входящий звонок             | `call_incoming`    | `telephony.service.ts`        |
| Запрос на изменение профиля | `profile_request`  | `profile.service.ts`          |
| Запрос на удаление аккаунта | `account`          | `account.service.ts`          |

### Гейты в `sendToUserCategory`

1. `notification_mutes` — категория выключена;
2. `master_enabled = false` — выключено всё;
3. тихие часы — **не отправляем вовсе** (а не «шлём без звука»): беззвучный баннер на
   залоченном экране в 03:00 — это всё ещё уведомление, которое просили не слать;
4. `sound = false` — не подавляет, а переводит сообщение в `sound: null`.

Тихие часы считаются в **локальном** времени пользователя: клиент присылает
`tzOffsetMinutes` (МСК = 180), сервер сдвигает UTC. Окно через полночь (22:00 → 07:00)
поддержано. `from == to` трактуется как «выключено», а не «тишина 24 часа».

Броадкасты поддержки (`sendBroadcastToUser`) и тихие data-пуши (`sendDataToTenant`)
**намеренно** не подчиняются ни одному гейту.

### Экран «Уведомления»

Секции: **Основное** (мастер-тумблер, звук) · **Тихие часы** (два time-пикера) ·
**Работа** · **Деньги** · **Клиенты** · **Прочее** · **Диагностика**.

## 5. Что требует действий владельца (вне кода)

1. **APNs-ключ в EAS** — без него Expo не сможет подписать запрос к APNs:
   ```bash
   cd mobile && eas credentials -p ios
   ```
   В разделе «Push Notifications: Manage your Apple Push Notifications Key» должен быть
   загруженный ключ. Если его нет — это второй возможный корень, и `POST /push/test`
   вернёт `InvalidCredentials`.
2. **Новая сборка обязательна.** Правка `aps-environment` — нативная. OTA (`eas update`)
   её **не доставит**: нужен `eas build` + новый TestFlight-билд.
3. **Firebase для Android** — нужен Google-аккаунт владельца: создать проект, скачать
   `google-services.json`, положить в `mobile/`, добавить
   `"googleServicesFile": "./google-services.json"` в `android` секцию `app.json`,
   загрузить FCM V1 key в `eas credentials`. До этого Android-пуши невозможны.
4. **`EXPO_ACCESS_TOKEN`** в `.env` на сервере — не обязателен сегодня, но обязателен
   в тот день, когда в аккаунте Expo включат «Enhanced Security for Push».

## 6. Fallback-поведение

| Ситуация                           | Поведение                                                                                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Старый клиент ↔ новый бэкенд       | Работает: новые категории просто не отображаются, гейты дефолтные (всё включено)                                                     |
| Новый клиент ↔ старый бэкенд       | `GET /notifications/settings` и `/push/*` дают 404 → экран показывает дефолты и ошибку теста; тумблеры категорий работают как раньше |
| Нет строки `notification_settings` | Всё включено, тихих часов нет                                                                                                        |
| Android без Firebase               | Регистрация пропускается с breadcrumb; экран честно пишет, что push не настроен                                                      |
| `EXPO_ACCESS_TOKEN` не задан       | Заголовок не отправляется — сегодняшнее поведение                                                                                    |
| Expo недоступен                    | `postToExpo` резолвится с `transportError`, вызывающий код не падает                                                                 |

## 7. Как диагностировать пуш за 10 секунд

**Ещё → Уведомления → Диагностика.** Три строки состояния (разрешение системы, устройство
зарегистрировано, среда доставки APNs) и кнопка **«Отправить тестовый пуш»**, которая
отправляет push самому себе и показывает **сырой вердикт Expo** — тикеты плюс квитанции
доставки, с готовой русской расшифровкой.

Результат имеет **три** состояния, а не два:

| Состояние                     | Значит                                                      |
| ----------------------------- | ----------------------------------------------------------- |
| 🟢 **Доставлено**             | Тикет `ok` **и** пришла квитанция `ok`. Только это — успех. |
| 🟡 **Отправлено, ждём ответ** | Expo принял, квитанция ещё не готова. Не успех и не провал. |
| 🔴 **Не доставлено**          | Явная ошибка тикета/квитанции/транспорта.                   |

> Почему это важно: `[].every(ok)` возвращает `true`. Наивная проверка рисовала бы зелёное
> «Доставлено» в самом частом случае — когда квитанции ещё нет, — то есть диагностика врала
> бы ровно так, как врал сам баг. Успех требует **положительного доказательства**.

Строка **«Среда доставки (APNs)»** показывает значение только если запущен **встроенный**
бандл (`Updates.isEmbeddedLaunch`). После OTA-обновления она честно пишет
«неизвестно (OTA)»: `runtimeVersion` = `appVersion`, поэтому этот JS может приехать на
старый бинарник с `aps-environment: development`, и утверждать «production» было бы
дезинформацией.

Расшифровки ошибок:

- `DeviceNotRegistered` → sandbox/production mismatch или переустановка;
- `InvalidCredentials` → APNs-ключ не загружен в EAS;
- `MismatchSenderId` → FCM-ключ не совпадает с `google-services.json`;
- `transportError` → сервер не достучался до Expo.

Через API (для отладки с сервера):

```bash
curl -s -X POST https://autexa.pw/api/push/test -H "Authorization: Bearer <JWT>" | jq
curl -s https://autexa.pw/api/push/tokens   -H "Authorization: Bearer <JWT>" | jq
```

`GET /push/tokens` возвращает токены **замаскированными** и только свои.

## 8. Acceptance criteria (проверка на физическом iPhone)

Требуется **новая сборка** (TestFlight), OTA недостаточно.

1. Установить билд → на первом входе iOS спросит разрешение на уведомления → «Разрешить».
2. Ещё → Уведомления → Диагностика:
   - «Разрешение системы» = **Выдано**;
   - «Устройство зарегистрировано» = **Да (1)**;
   - «Среда доставки (APNs)» = **production** (если стоит «неизвестно (OTA)» — вы
     запустили OTA-бандл поверх старого бинарника; проверять надо на свежей сборке).
     Любое другое значение здесь — баг.
3. Нажать «Отправить тестовый пуш», свернуть приложение. Через несколько секунд —
   баннер «Проверка уведомлений», в карточке результата зелёное **«Доставлено»**.
   Жёлтое «Отправлено, ждём ответ» — не баг: повторите через минуту, должно стать
   зелёным. Красное «Не доставлено» с текстом ошибки — баг (текст = причина).
4. Выключить «Звук и вибрация» → повторить тест → баннер приходит **беззвучно**.
5. Включить «Не беспокоить», выставить интервал так, чтобы **текущее время попало внутрь**
   → попросить второго сотрудника закрыть чек → пуш «Чек закрыт» **не приходит**.
   Выставить интервал мимо текущего времени → приходит. Приход в тихие часы — баг.
6. Выключить «Все уведомления» → категории гаснут и становятся неактивными → ни один
   рабочий пуш не приходит. Приход — баг.
7. Выключить одну категорию (например «Входящие звонки») → событие этой категории не
   приходит, **остальные продолжают приходить**. Пропажа остальных — баг.
8. Перезапустить приложение → все тумблеры сохранили значения. Сброс — баг.

## 9. Ограничения (честно)

- Доставка на **физическом iPhone из TestFlight** на момент написания не проверялась:
  требуется новая сборка и устройство владельца. Проверено: содержимое
  `Autexa.entitlements` и `Info.plist` после `prebuild --clean`, разрешение конфига во всех
  трёх ветках, миграция и SQL-запросы на живом PostgreSQL 16, backend/mobile/frontend
  typecheck + lint + build + тесты.
- Наличие APNs-ключа в EAS не проверялось (нужен доступ к аккаунту владельца) — если
  ключа нет, тест покажет `InvalidCredentials`.
- Android-пуши остаются невозможны до заведения Firebase-проекта (§5.3).
