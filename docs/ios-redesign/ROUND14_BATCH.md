# Round 14 — крупный батч 2026-08-03 (v3.3.0)

Пять зон: Sentry-находки, корректировка платежей поставщикам, режим «Кассир», периоды денег, уведомления. Ветка `feat/round14-batch` → `refactor/full-audit-2026`. Миграции 144–151.

## 1. Sentry: logout, push-шум, продление сессии

- **Logout падал 500** у пользователя без тенанта (superadmin): заглушка `nil-UUID` нарушала внешний ключ, токен НЕ отзывался. Теперь заглушка нормализуется в NULL, а при любом отказе БД (включая RLS-политику) запись идёт через admin-пул. Токен попадает в blacklist всегда — иначе 500, не тихий успех.
- **Push-шум**: сетевые сбои Expo (`ERR_NOTIFICATIONS_*`) стали тихими ретраями с breadcrumb; реальные ошибки регистрации (APNs entitlement, projectId) по-прежнему видны.
- **Принудительные разлогины** (148 событий): добавлен `POST /auth/refresh`. После adversarial-ревью — одноразовый обмен: claim старого jti прямо в БД (мимо 30-секундного кэша), отозванный токен новый выпустить не может, старая линия живёт ещё 2 минуты (in-flight запросы), impersonation блокируется сервером (403). Web без refresh — осознанно.

## 2. Поставщики: сторно и возврат

Ошибочный платёж **сторнируется** с причиной: `FOR UPDATE` + проверка `reversed_at` (двойное сторно невозможно), баланс поставщика компенсируется в той же транзакции, авто-платёж при приёмке возвращает поставку в долг. **«Возврат от поставщика»** — строка с отрицательной суммой. Ничего не удаляется физически — зачёркнуто с аудит-следом. «Закупка товара» в Расходах не считает сторнированные; в журнале возврат показывается плюсом. Новая ячейка матрицы **«Корректирует платежи поставщикам»** (мигр. 145) — по умолчанию только Директор. Возвраты брака теперь маркируются структурно (`kind`), а не по тексту комментария.

## 3. Режим «Кассир» (спека — `CASHIER_MODE_SPEC.md`)

Конвейер **Принят → В работе → Готова → Оплачена → Выдана**. Админ принимает машину, назначает **нескольких исполнителей**, ставит **место** («возле задних ворот» — справочник в настройках) и комментарий; мастер видит машину на доске и работает (правит состав только с правом «Изменяет назначенный заказ»); кассир в своём экране «Оплата» ищет по госномеру, даёт скидку, принимает нал/карту/смешанную; мастер выдаёт.

- **Деньги рождаются один раз** — в момент «Оплачено»: до этого заказ отложен (ни выручки, ни склада, ни зарплат). Выдача без оплаты невозможна (400). Переоткрытие проведённого чека запрещено (был путь к двойному списанию склада).
- **Таб-бар меняется по роли** без единой правки Swift (нативный бар уже параметризован): кассир — Смены + центр «₽ Оплата», админ — Приёмка + Доска, мастер — как был, режим выключен — байт-в-байт легаси.
- **Кассир — строгая роль-пресет** (создаётся в один тап), совмещение с мастером не предполагается; после ревью добавлен узкий роут `PATCH /checks/:id/accept-payment` под правом «Приём оплаты» — иначе кассир по пресету физически не мог принять оплату (critical-находка).
- Смена режима блокируется, пока есть незакрытые заказы — со списком, что закрыть (считаются только реально видимые на доске).
- Push по цепочке: назначен → исполнителям, готова → кассирам, оплачено → исполнителям.

## 4. Деньги по периодам

- **«За какой месяц»** у выплат ЗП и платежей поставщикам: платишь в августе за июль — расход уходит в июль. Касса и лента «Расходы» всегда показывают факт. Период отправляется только при осознанном выборе месяца, а period-расход попадает лишь в срезы, покрывающие месяц целиком — дневные и недельные отчёты не задваивают.
- **Ставка мастера по месяцам** (мигр. 150): смена на прошлый месяц пересчитывает только его (снапшот-щит не даёт «протечь» на текущий), на будущий — применится автоматически 1-го числа. Персональные проценты услуг и товарные комиссии остаются приоритетнее. Правка старого чека считает по ставке ЕГО месяца.
- **Выплаты вне программы** (маркетолог, уборщица): получатель-строка, сумма, месяц — отдельная категория расходов (не «Зарплата», иначе исключалась бы из прибыли по имени).

## 5. Уведомления: найден корень «пушей нет»

Плагин `expo-notifications` объявлялся без `mode` → в **production-сборку** уезжал `aps-environment: development`. Приложение регистрировалось в sandbox APNs, сервер слал в production → Apple отбивал `BadDeviceToken`, но Expo-тикет отвечал `ok`, квитанции никто не читал, а `logger.error` не доходил до Sentry. Идеально невидимая поломка.

Исправлено: `mode: production` + `enableBackgroundRemoteNotifications` (тихие data-пуши раньше не будили приложение — `UIBackgroundModes` отсутствовал). Добавлены чтение квитанций доставки, агрегированные ошибки в Sentry, `Authorization` из `EXPO_ACCESS_TOKEN`, `POST /push/test` и **блок диагностики в настройках**: разрешение системы, наличие токена, режим APNs, кнопка «Отправить тестовый пуш» с текстом реальной ошибки.

**Гибкие настройки** (мигр. 151): мастер-тумблер, тихие часы, звук, и 6 новых категорий (готова, оплачено, запись, звонок, профиль, аккаунт) — раньше они не глушились вовсе.

**Требует владельца:** Android-пуши невозможны до создания Firebase-проекта (`google-services.json` + FCM-ключ в EAS); APNs-ключ в EAS-креденшелах проверяется командой `eas credentials -p ios`.

## Контроль качества

Adversarial-ревью в 5 линз нашло **19 находок**, включая critical (кассир не мог принять оплату), три high в auth-refresh (отозванный токен мог обновиться из-за кэша, бесконечный форк линии, обход блокировки impersonation) и high-регрессию (старые сборки падали на новом виде документа в журнале). Все закрыты до выкатки. Агент уведомлений дополнительно поймал ложь в собственной диагностике (зелёное «Доставлено» без квитанции).
