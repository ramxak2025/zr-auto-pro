# Кассовая смена v2: кассиры, сейф, размен, персональная ответственность (2026-08-21)

Крупное обновление режима кассовой смены по требованиям владельца (пункты 5.1–5.3
августовского списка правок). Backend: миграция `155_cash_shift_safe_and_attribution.sql`.

## Проблема / motivation

1. Не было настройки «кто принимает оплату» — право жило только в матрице ролей;
   режим включался даже без единого кассира.
2. Не записывалось, **кто фактически принял деньги** — ответственность за кассу
   нельзя было разнести по людям.
3. Не было сейфа и пересменки: закрытие смены никак не связано с открытием
   следующей, «размен на завтра» держали в голове.
4. Кассир не мог продать в рассрочку.
5. Владелец не получал уведомлений о закрытии кассы; кассир — об инкассации.
6. Админ в режиме смены получал полную кассу с блоком оплаты, хотя должен только
   принимать машины и отправлять их на доску.

## Архитектура решения

### Кто принимает оплату (5.1)

- Новая колонка `tenants.payment_acceptors JSONB` — явный список user id.
  - `NULL` (дефолт) — прежнее поведение: право `accept_payment` из матрицы роли.
  - Непустой список — принимают **только** перечисленные (+ owner-class всегда).
- Резолвер эффективного кассира в `checks.service.ts` применяется во всех точках:
  `getPosSettings.isCashier`, гейт `accept-payment`, активация отложенного чека,
  `forceDeferred` при создании, рассылка пушей «машина готова».
- Экран «Кто принимает оплату» в настройках компании (mobile + web):
  `GET /checks/payment-acceptors` (список сотрудников с резолвом) +
  `PATCH /checks/pos-settings { paymentAcceptorIds }` (гейт `settings_manage`).
- Гард включения режима: `shiftModeEnabled false→true` без единого активного
  не-owner-class эффективного кассира → 409 «Некому принимать оплату…».
- Роль «Кассир» остаётся клиентским пресетом (`CASHIER_ROLE_PRESET`), создаётся
  в один тап из редактора ролей; пресету включён `sellInstallment`.

### Атрибуция «кто принял» (5.1)

- `checks.accepted_by / accepted_at` — проставляются в точках «рождения денег»:
  создание активного чека и активация отложенного (оба пути: accept-payment и
  `update {isDeferred:false}`). История не бэкфиллится — fallback `master_id`.
- «Движение денег»: фильтр по сотруднику переведён на
  `COALESCE(accepted_by, master_id)` — деньги видны на том, кто их принял.

### Сейф, размен, пересменка (5.2)

- Таблица `safe_transactions` (deposit / collection / adjustment, RLS).
  Баланс = Σdeposit + Σadjustment − Σcollection.
- Закрытие смены: `POST /cash-shifts/:id/close` принимает `toSafeAmount`
  (0..closing) и `settlements[]` (сдача по сотрудникам). `carryover_amount =
closing − toSafe` — «размен на завтра»; следующее открытие подставляет его
  дефолтом, если `openingAmount` не передан.
- Сдача по сотрудникам: `cash_shift_settlements` (expected из разбивки
  `perAcceptor` по `accepted_by`, actual — введённая сумма; Σactual должна
  равняться `closingAmount` ± 0.01).
- Инкассация: из кассы — прежняя `cash_collections`; из сейфа —
  `POST /cash-shifts/safe/collect` (без открытой смены). Подтверждение кассиром
  убрано по решению владельца — кассиру уходит пуш.
- «Движение денег» получило кошельки `wallets {drawer, safe}` и строку
  «Инкассации» по дням.

### Уведомления

Две новые категории (`NotificationCategory`):

- `cash_shift_closed` → директорам: «Касса закрыта: нал X, карта Y, в сейф Z,
  размен M, расхождение D».
- `cash_collection` → эффективным кассирам: «Инкассация N ₽ из кассы/сейфа,
  остаток M ₽».

Пуши шлются после COMMIT, best-effort, уважают глобальные настройки и mute.

### Рассрочка у кассира (5.2)

`PATCH /checks/:id/accept-payment` принимает `paymentMethod: 'installment'` +
`installment { nextPaymentDate }`: ноги чека = первый взнос, остаток — план
рассрочки (`createPlanForCheckTx` в той же транзакции активации). Гейт
`sell_installment`. UI — способ «Рассрочка» в AcceptPaymentScreen.

### Админ и доска (5.3)

- Админ, не выбранный принимающим, автоматически получает `orderMode`: касса без
  блока оплаты и без «Отложить чек», CTA — **«Отправить на доску»** (сервер сам
  паркует заказ в первую колонку).
- Доска: **тап** по карточке → сразу заказ-наряд; **лонг-пресс** → выбор этапа;
  пункт «Изменить комментарий» (гейт `checks_edit`, серверный гейт комментария
  расширен для конвейера); комментарий виден на карточке; фото исполнителей
  32pt (`assignees[].avatar`) с fallback на инициалы; «Выдана» для неоплаченного
  заказа задизейблена с подписью «Сначала оплата у кассира» (серверный 400-гейт
  существовал и сохранён).
- Журнал: при включённом режиме чеки тонированы по оплате (неоплачен — оранжевый
  - бейдж, оплачен — зелёная полоса).

## Fallback-стратегия

- Старые клиенты (OTA-лаг): закрытие смены без `toSafeAmount` = всё остаётся в
  кассе (`carryover = closing`); `settlements` опциональны; все новые поля
  контракта аддитивные.
- `payment_acceptors = NULL` — поведение до обновления байт-в-байт.
- Выключенный режим кассовой смены — поведение всех экранов прежнее.
- Android: только кроссплатформенные RN-компоненты, отдельного native-кода нет.

## Acceptance criteria (проверка владельцем на iPhone)

1. Настройки компании → «Кто принимает оплату»: выбрать вручную сотрудников;
   снять всех при включённом режиме → 409-текст; «Сбросить к ролям».
2. Админ не в списке: центральная кнопка кассы — без блока оплаты, CTA
   «Отправить на доску», заказ появляется в первой колонке доски.
3. Кассир: принять оплату «Рассрочка» с первым взносом → чек активен, план виден
   в разделе «Рассрочка».
4. Закрытие смены: разбивка по сотрудникам, «В сейф» 45 000 из 50 000 → «Останется
   на размен: 5 000»; следующее открытие предзаполнено 5 000; владельцу пришёл
   пуш «Касса закрыта…».
5. Инкассация из сейфа владельцем → кассиру пуш «Инкассация … остаток …»;
   баланс сейфа уменьшился; в «Движении денег» карточки Касса/Сейф сходятся.
6. Журнал в режиме смены: неоплаченные оранжевые, оплаченные с зелёной полосой.
7. Доска: тап открывает заказ; лонг-пресс — этапы; «Выдана» недоступна до оплаты.

## Ограничения (честно)

- `accepted_by` не бэкфиллится: смены за прошлые периоды показывают разбивку по
  `master_id`.
- Расходы по-прежнему считаются наличными из ящика (у `expenses` нет признака
  нал/карта) — при безнал-расходах expected кассы может расходиться (известное
  ограничение, зафиксировано до обновления).
- Сейф один на тенанта (мульти-локации не разделяются).
- Проверено: typecheck/lint/build backend+frontend, typecheck/lint + 636 jest
  mobile. Прогона на физическом устройстве в этой сессии не было — чек-лист выше.
