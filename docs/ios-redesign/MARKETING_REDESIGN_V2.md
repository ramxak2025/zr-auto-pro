# Маркетинг V2 — журнал отправок, видимые гарантии, безопасные дефолты

Дата: 2026-07-27 · Ветка: `feat/round12-batch` (Round 12, пункт 8)

## Проблема (словами владельца)

«В Маркетинге каша, непонятно как что работает. Хочу СМС с запросом отзыва, но
боюсь, что (а) пойдут ещё какие-то смс клиентам, (б) клиенту придёт 10 смс».

Разведка показала: железные гарантии УЖЕ были на сервере, но невидимы.
Все 7 путей отправки идут через единый гейт `guardAndLogSend`
(`backend/src/marketing/marketing.service.ts`): потолок 3 сообщения клиенту за
24 ч поперёк всех типов, окно точного дубля 1 ч, dedup-ключи на сущность,
race-safe claim `UNIQUE(tenant_id, dedup_key)` (мигр. 124 `sent_messages`).
Но:

1. `sent_messages` писался и НЕ читался — ни endpoint'а, ни экрана;
2. небезопасные дефолты ON: запрос отзыва, подтверждение записи и напоминание
   о записи рождались включёнными — «подключил интеграцию → пошли смс молча»;
3. заглушки провайдеров `'sms'`/`'email'` возвращали `success:true`, ничего не
   отправляя — фантомное «отправлено» (включая карточку «Мегафон ВАТС»);
4. реестр авто-рассылок показывал 4 сценария из 6;
5. лимиты — приватные константы, предпросмотра рассылки не было.

## Архитектура решения

### Backend (`backend/src/marketing/`, мигр. 141)

- **`GET /marketing/sent-messages`** — курсорная лента журнала (keyset
  `(tenant_id, sent_at DESC, id DESC)`, индекс в мигр. 141; курсор — raw
  pg-text, микросекундный урок чеков). Фильтры: `type`, `status`, `clientId`,
  `dateFrom/dateTo` (московский полуинтервал). Ответ несёт
  `meta: { perClient24hCap, exactDupWindowHours }` — UI показывает гарантии из
  первоисточника, не хардкодом. Записи канала telegram помечены
  `toOwner: true` (бот пишет владельцу, не клиенту). Текста сообщения в
  журнале нет — сервер хранит только `content_hash`. Гейт `marketing_access`.
- **`POST /marketing/broadcast/preview`** — dry-run ручной рассылки: тот же
  `resolveSegment` + `getAdapterRowFor`, что и у отправки, но НИЧЕГО не шлёт.
  Возвращает `{ recipientsCount, sample (до 5 имён + маскированные телефоны),
channel, channelConnected, perClient24hCap }`. Гейт `marketing_manage`.
- **`GET /marketing/auto-mailings`** — расширен до ВСЕХ 6 сценариев (было 4):
  добавлены подтверждение записи и напоминание о записи (`booking_settings`).
  У каждого: `enabled`, `humanTitle`, `trigger` (описание триггера),
  `lastSentAt` (max(sent_at) из журнала; installment/service и booking
  confirm/reminder различаются префиксом `dedup_key`).
- **Миграция `141_marketing_safe_defaults.sql`** — только `ALTER COLUMN … SET
DEFAULT false` для `review_settings.auto_send_enabled`,
  `booking_settings.notify_client_on_create`, `booking_settings.reminder_enabled`
  - индекс журнала. **Без backfill**: работающие рассылки существующих
    тенантов не выключаются. `bookings.service.ts` приведён в соответствие
    (tenant-less зеркало и COALESCE-дефолты INSERT-ветки → false).
- **Заглушки** `SmsGenericAdapter`/`EmailAdapter` теперь возвращают
  `success:false` + «Канал не настроен», а типы `'sms'`/`'email'` исключены из
  выбора канала (`getAdapterRowFor` + `getAdapter`,
  `NON_SENDING_PROVIDER_TYPES`): явный `integrationId` такой строки → честный
  `no_provider` без сожжённого dedup-ключа. Фантомных «отправлено» больше нет.
- `guardAndLogSend`, race-safe claim, cron-логика — **не тронуты**.

### Shared (`shared/types`, `shared/api/createServices.ts`)

`SentMessage`, `SentMessageType`, `SentMessagesMeta`, `SentMessagesResponse`,
`BroadcastPreviewRequest`, `BroadcastPreview`; `AutoMailingOverview` расширен
(`booking_confirm`/`booking_reminder` + optional `humanTitle`/`trigger`/
`lastSentAt` — старый сервер совместим). `marketingApi.getSentMessages()`,
`marketingApi.previewBroadcast()`.

### iOS/Android (RN, `mobile/src/`)

- **`MessagesJournalScreen`** («Журнал отправок», `MoreStack →
MessagesJournal`): infinite-лента по курсору, фильтр-чипы по типу, строка =
  тип-иконка + кому + тип по-русски + канал + статус + время; telegram-записи
  подписаны «в чат владельца»; ошибки — с текстом. Пустое состояние — витрина
  гарантий («Здесь видно каждое сообщение… Не больше 3 сообщений клиенту за
  24 часа, повторы отсекаются автоматически» — числа из `meta`).
- **`MarketingScreen`** (хаб): вход «Журнал отправок» в группе «Работа с
  клиентами», сразу под «Рассылками».
- **`MailingsScreen`**:
  - ручная рассылка — кнопка «Проверить и отправить»: сначала dry-run preview,
    затем подтверждение «Уйдёт N клиентам через <канал>» + текст + примеры
    получателей + строка про потолок 3/24ч → Отменить/Отправить. Если preview
    недоступен (старый сервер/сеть) — прежнее общее подтверждение, отправка не
    блокируется;
  - вкладка «Авто» — единый реестр всех 6 сценариев: живой тумблер (каждый
    пишет своим существующим endpoint'ом), описание триггера, «Последняя
    отправка: …», переход к настройке (booking-сценарии → `BookingSettings`).
    Включение любого сценария — через confirm с объяснением; для «Запроса
    отзыва» — с реальным шаблоном сообщения. Выключение — мгновенно.
- **`MarketingSettingsScreen`**: тумблер «Отправлять автоматически» (отзыв)
  при включении показывает confirm с текущим шаблоном и объяснением «уйдёт
  ОДИН раз после каждого закрытого заказ-наряда».
- **`IntegrationsScreen`**: карточка «Мегафон ВАТС» больше не обещает SMS
  (транспорта нет) — «Звонки через Мегафон» + подсказка использовать SMS.RU /
  WhatsApp для SMS.

### Web (`frontend/src/components/marketing/`)

- Новый **`JournalView`** — таб «Журнал» в `MarketingPage` (сразу после
  «Рассылок»): баннер гарантий из `meta`, фильтр-чипы, лента, «Показать ещё».
- **`BroadcastsView`**: двухшаговая отправка (preview-панель с N получателей,
  текстом, примерами и строкой про потолок → Отменить/Отправить); реестр
  авто-сценариев — все 6, живые тумблеры + ConfirmDialog при включении (для
  отзыва — с реальным шаблоном), «Последняя отправка».
- **`IntegrationsView`**: типы `'sms'`/`'email'` исключены из создания
  (`CREATABLE_MESSAGING_TYPES`); legacy-строки остаются видимыми/удаляемыми.

## Fallback-стратегия

- Старый сервер (без новых endpoint'ов): мобильный preview падает в прежнее
  общее подтверждение; `AutoMailingOverview` новые поля optional — реестр
  показывает `summary`; журнал вернёт 404 → стандартная ошибка запроса.
- Тенанты с уже включёнными рассылками: мигр. 141 не делает backfill —
  ничего не выключается.
- Тенант, у которого единственный канал — 'sms' («Мегафон ВАТС»): все
  отправки честно `no_provider` (раньше — фантомные «отправлено»); review-jobs
  помечаются `skipped`, UI подсказывает подключить SMS.RU/WhatsApp.

## Acceptance criteria (проверка на iPhone владельцем)

Страх (а) «пойдут ещё какие-то смс клиентам»:

1. Маркетинг → Рассылки → «Авто»: видны ВСЕ 6 сценариев с тумблерами.
   Все выключенные — выключены; ничего не отправляется молча (для нового
   тенанта всё OFF по умолчанию).
2. Маркетинг → «Журнал отправок»: видно каждое отправленное сообщение (тип,
   кому, когда, канал, статус). Пусто = ничего не уходило.
3. Включение «Запроса отзыва» (в реестре или в Настройках) показывает ТОЧНЫЙ
   текст будущего сообщения до включения.

Страх (б) «клиенту придёт 10 смс»:

4. В журнале и в реестре видна гарантия «не больше 3 сообщений клиенту за
   24 ч, повторы отсекаются» (число приходит с сервера).
5. Ручная рассылка: перед отправкой видно «Уйдёт N клиентам через <канал>» и
   предупреждение о потолке; после отправки — счётчики
   Отправлено/Пропущено/Ошибок (пропущенные = защита от спама).
6. Повторная отправка той же рассылки в течение часа даёт «Пропущено» вместо
   повторных SMS — виден в журнале только один раз.

Что считается багом: любое сообщение клиенту, не отражённое в журнале;
«отправлено» при неподключённом канале; включённый по умолчанию сценарий у
нового тенанта.
