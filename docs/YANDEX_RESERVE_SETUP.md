# Резервный вход через Яндекс (API Gateway) — план и инструкция

Дата: 2026-07-05. Контекст: в Дагестане мобильные операторы (подтверждено на Мегафоне) периодически
режут трафик к обычным VDS-адресам и душат VPN-протоколы. Ночь 04–05.07 доказала: сервер (Beget,
212.8.229.254) безупречно отвечает из всех дата-центров РФ и Европы, но путь «телефон → сервер»
мигает как без VPN, так и с VPN (заграничные выходы VPN дополнительно режутся на границе).

**Идея резерва:** телефон ходит на хост Яндекс Облака (`*.apigw.yandexcloud.net` — IP-диапазоны
Яндекса, наилучшие шансы работать даже в «жёсткие» окна), а Яндекс проксирует запросы на наш
сервер по магистрали между дата-центрами (этот путь доказанно чистый). Кольцо переключения хостов
в приложении (`mobile/src/api/apiHosts.ts`) уже готово — резерв добавляется одной строкой в
`extra.apiFallbackUrls`, после чего нужен native build для iOS и Android. OTA допустим только для
уже установленной сборки с тем же совместимым `runtimeVersion` и набором native-модулей.

---

## Шаг 1 — владелец (5 кликов в консоли Яндекс Облака)

1. Открыть https://console.yandex.cloud → выбрать каталог (тот же, где SpeechKit: `b1gfk6a9nl97bb5f3hqt`).
2. В меню слева найти **API Gateway** (раздел Serverless) → **Создать API-шлюз**.
3. Имя: `autexa-reserve`. Описание можно пустое.
4. В поле «Спецификация» стереть всё и вставить YAML ниже — целиком, без изменений.
5. Нажать **Создать**. Через ~30 секунд шлюз получит «Служебный домен» вида
   `https://d5dXXXXXXXX.apigw.yandexcloud.net` — **скопировать этот адрес и прислать в чат**.

```yaml
openapi: 3.0.0
info:
  title: autexa-reserve
  version: 1.0.0
paths:
  /api/{proxy+}:
    x-yc-apigateway-any-method:
      x-yc-apigateway-integration:
        type: http
        url: https://autexa-cloud.ru/api/{proxy}
        headers:
          Host: autexa-cloud.ru
          '*': '*'
        query:
          '*': '*'
      parameters:
        - explode: false
          in: path
          name: proxy
          required: true
          schema:
            type: string
          style: simple
```

**Грабли HTTP-интеграции Яндекса (наступили 05.07, не повторять):**

1. `method: ANY` — НЕ «передавай метод как есть», а литеральный HTTP-метод «ANY» →
   Node/llhttp отвергает с 400 до всякой логики. Чтобы метод проходил насквозь,
   поле `method` просто **не указывать**.
2. По умолчанию интеграция передаёт из исходного запроса **только User-Agent**:
   ни остальных заголовков (Content-Type! Authorization!), ни query-параметров.
   Симптомы: POST c JSON → `400 phone should not be empty` (тело не распарсено без
   Content-Type), любой авторизованный запрос → 401, все `?clientId=…` теряются.
   Лечение: `headers: {'*': '*'}` + `query: {'*': '*'}`.
3. `Host: autexa-cloud.ru` пином — иначе на сервер уедет Host шлюза
   (`*.apigw.yandexcloud.net`) и nginx отдаст запрос default-блоку, а не блоку
   autexa-cloud.ru. Работает, пока default совпадает, но это лотерея — пиним.

Стоимость: до 100 000 запросов в месяц — бесплатно, дальше копейки (~30 ₽ за миллион).
Резерв используется только когда основной путь не работает.

## Шаг 2 — Claude (после получения адреса шлюза)

1. Проверка насквозь: `GET https://<шлюз>/api/health` → 200, `POST /api/auth/login` (демо-аккаунт) → 201.
2. Rate-limit: убедиться, что backend не собьёт всех пользователей резерва в один IP-бакет
   (весь трафик шлюза приходит с немногих IP Яндекса). Смотреть, как `RateLimitGuard` берёт IP;
   при необходимости учитывать `X-Forwarded-For` от шлюза (backend — зона повышенной
   ответственности, менять точечно).
3. `mobile/app.json` → `extra.apiFallbackUrls: ["https://<шлюз>/api"]` → гейты → коммит → **native build**
   на обе платформы. OTA допустим только для уже установленной сборки с тем же совместимым
   `runtimeVersion` и набором native-модулей; на старые App Store/TestFlight-сборки с иным native
   runtime этот пакет не публиковать.
4. Тест с телефона владельца в «плохое» окно.

## Ограничения (честно)

- Тело запроса через шлюз ≤ 3,5 МБ: **загрузка фото через резерв может не пройти** (остальное —
  касса, чеки, склад, отчёты — целиком в лимите). Вариант на потом: загрузки фото прибивать к
  основному хосту.
- В минуты тотального «белого списка» гарантий не даёт никто; диапазоны Яндекса — лучший из
  доступных шансов. Если и это подведёт — следующий кандидат: VK Cloud / ngenix.
- Ответ владельцу серверу приходит с IP Яндекса, а не с IP клиента: в логах nginx источником будет
  шлюз (реальный IP — в заголовке `X-Forwarded-For`).

## Попутный фикс утренним окном

`zr-auto-pro-frontend-1` помечен unhealthy: healthcheck ходит на `http://localhost/`, а `localhost`
внутри контейнера резолвится в `::1` (IPv6), тогда как nginx слушает только `0.0.0.0:80` → connection
refused. Сайт работает (снаружи 200). Фикс — одна строка в `docker-compose.yml`:
`wget -qO- http://127.0.0.1/` вместо `http://localhost/`.
