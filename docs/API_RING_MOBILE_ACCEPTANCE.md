# Приёмка мобильного входа и API-кольца

Дата плана: 2026-07-18. Проверяем production-like **native build** текущей ветки на физических iPhone и Android. Симулятор/эмулятор и Jest не заменяют эту приёмку.

## Кольцо

- H1 — `https://autexa.pw/api`
- H2 — `https://autexa-cloud.ru/api`
- H3 — `https://d5dpq4hcfoor5l4q1a97.wnq2w1o5.apigw.yandexcloud.net/api`

Нужны тестовый tenant, корректный и заведомо неверный пароль, доступ к server/proxy-логам и способ блокировать FQDN по одному (тестовый VPN/DNS-фильтр или HTTPS-прокси). Для каждого прогона фиксировать: OS/модель, build, тип сети, VPN, заблокированные хосты, фактически использованный Host, длительность и результат.

## Матрица входа

Повторить каждую строку на iOS и Android:

| Сеть                         | Холодный старт и верный пароль            | Неверный пароль                                                      | Повторный запуск                          |
| ---------------------------- | ----------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------- |
| Мобильная сеть, VPN выключен | [ ] вход; открыть Дашборд, Склад и Журнал | [ ] один `POST /auth/login`, понятная 401, без обхода других алиасов | [ ] сессия восстановлена, Login не мигает |
| Wi-Fi, VPN выключен          | [ ] то же                                 | [ ] то же                                                            | [ ] то же                                 |
| VPN включён                  | [ ] то же                                 | [ ] то же                                                            | [ ] то же                                 |

Критерий: нет бесконечного спиннера, HTML/страница оператора не принимается за API, валидная сохранённая сессия не удаляется из-за timeout/502, а поздний ответ старой сессии не меняет нового пользователя.

## Отказ отдельных хостов

Перед сценарием принудительно закрыть приложение. Блокировать весь FQDN, а не только `/health`.

1. [ ] Заблокировать H1; H2 и H3 оставить доступными. Вход проходит через один из резервов.
2. [ ] Заблокировать H2; H1 и H3 оставить доступными. Вход проходит, запросов к H2 после выбора рабочего маршрута нет.
3. [ ] Заблокировать H3; H1 и H2 оставить доступными. Вход проходит напрямую, без зависимости от шлюза.
4. [ ] Сделать H2 сохранённым активным: временно оставить доступным только H2, запустить приложение и дождаться успешного API-запроса, затем закрыть приложение. Заблокировать H2, открыть H1/H3 и перезапустить — сохранённый H2 проверяется, отвергается и не удерживает вход.
5. [ ] Аналогично сделать сохранённым H3; затем заблокировать H3 и открыть H1/H2 — вход восстанавливается через прямой хост.
6. [ ] По очереди оставить доступным только H1, только H2 и только H3 — каждый одиночный survivor обеспечивает вход.
7. [ ] Заблокировать все три — одна попытка входа завершается честной сетевой ошибкой примерно за 30 секунд, без вечного ожидания и без трёх параллельных login POST.
8. [ ] После пункта 7 разблокировать один хост или сменить сеть/VPN и нажать «Проверить снова» — вход/сессия восстанавливается без очистки данных и переустановки.

Для удалённого старого значения отдельно проверить debug-сценарий: записать в AsyncStorage `active_api_base_v1=https://removed-old.example/api`, перезапустить и убедиться, что запросов на этот адрес нет, ключ очищен, используется только текущее кольцо.

## Смена маршрута с открытым приложением

Войти один раз, затем на каждом переходе открыть экран, который делает свежий GET (`pull-to-refresh` подходит):

- [ ] Wi-Fi → мобильная сеть;
- [ ] мобильная сеть → Wi-Fi;
- [ ] VPN off → on;
- [ ] VPN on → off;
- [ ] включить/выключить VPN, пока приложение в background, затем вернуть его в foreground;
- [ ] начать запрос на старой сети, сменить маршрут до ответа — поздний результат старого маршрута не должен откатить выбранный хост и не должен завершить новую auth-сессию.

Критерий: следующий запрос ждёт ограниченный fresh selector, выбирает доступный хост, пользователь остаётся авторизован; при полном кратком разрыве показывается корректный recovery/offline UI, который исчезает после восстановления.

## Что приложить к результату

- отметки по всем пунктам отдельно для iOS и Android;
- времена cold login и восстановления после смены сети;
- Host/status из proxy/backend-логов, особенно число `POST /auth/login`;
- скриншот каждой терминальной ошибки;
- carrier, Wi-Fi и VPN-провайдер для любого воспроизводимого отказа.
