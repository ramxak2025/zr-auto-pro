# Движение денег: почему оборот не сходился с разбивкой, и как починено

Дата: 2026-07-05. Жалоба владельца: «оборот ≠ наличные + картой + по гарантии».

## Причины (подтверждены построчно)

1. **Рассрочка.** Оборот считался по начислению (`SUM(total_revenue)`), разбивка — по кассе
   (`SUM(cash_amount)/SUM(card_amount)`). Чек в рассрочку попадает в оборот всей суммой, в
   разбивку — только первым взносом; остаток долга не имел строки. Погашения писались только в
   `installment_payments` и не были видны ни одному отчёту.
2. **Фантомная нога (только мобилка).** Payload слал `cashAmount: finalCash || undefined` —
   при правке чека со сменой способа оплаты старая нога выживала в БД → разбивка могла
   ПРЕВЫШАТЬ оборот.
3. Попутно: касса мастера «сегодня» теряла первый взнос рассрочки; чеки POS-режима смен
   (миграция 092) закрывались с нулевыми ногами; CHECK-констрейнт из 001 не допускал
   `'installment'` (прод правился руками — свежая БД падала бы).

## Дизайн фикса

- Оборот остаётся по начислению. Разбивка — **4 корзины**: Наличные, Картой, По гарантии,
  **Рассрочка (долг)** = `GREATEST(total_revenue − cash − card, 0)` по installment-чекам.
  **Тождество: cash + card + warranty + installmentDebt = total — копейка в копейку.**
- Отдельное информационное поле **«Погашения рассрочки»** (`installmentPaid`) — по дате платежа
  из `installment_payments`; в оборот не входит (деньги за прошлые продажи).
- Новые поля контракта опциональные (`installmentDebt?`, `installmentPaid?`) — старые клиенты
  и окно деплоя не ломаются; UI рендерит строки только когда поле пришло числом и > 0.

## Что изменено

- **Миграция 117** — CHECK-констрейнт `payment_method` перевешен на полный список (через
  `pg_constraint`, `NOT VALID` + guarded `VALIDATE`, `lock_timeout 5s` — не роняет старт).
- **Миграция 118** — разовый ремонт однозначно битых строк: фантомные ноги (card+cash>0 и
  зеркально), гарантия с ногами, shift-mode-чеки с нулевыми ногами. `cash_card`/`installment`
  не тронуты (раскладку не восстановить).
- **checks.service.ts** — нормализация ног при смене способа оплаты во ВСЕХ четырёх путях
  записи (update / activateDeferred / fullUpdate / editClosedCheck); запрет перевода чека в
  `'installment'` правкой (план не создаётся — был бы вечный фантомный долг); кап ног
  `cash_card`/`installment` к total в create(); `||0` против NULL-ног.
- **returns.service.ts** — возврат чека с открытым планом рассрочки отклоняется
  («сначала закройте рассрочку»).
- **salary.service.ts** — взнос рассрочки учитывается в кассе мастера (обе ноги: web может
  разбивать взнос на нал+карту).
- **reports.service.ts** — корзина долга + погашения в cashflow и dashboard-v2
  (`cashPosition.total` не менялся — cash+card+warranty, как раньше).
- **Мобилка** — payload шлёт ноги явными числами (0 ≠ undefined); CashFlowScreen: строка
  «Рассрочка (долг)», teal-строка «Погашения рассрочки +X ₽ (не входит в оборот)», иконки
  cash_card/installment вместо ложного щита гарантии; DashboardScreen: те же строки в
  CashPositionCard. **Web** — паритет на CashFlowPage; кламп ног в CheckCreatePage; кнопка
  «Рассрочка» скрыта в режиме правки (как в мобилке).

## Приёмка на телефоне

1. Движение денег: Наличные + Картой + Гарантия + Рассрочка (долг) = Итого, копейка в копейку.
2. Чек «наличными» → правка → «картой»: сумма ушла из «Наличные» в «Картой» целиком.
3. Принять платёж по рассрочке → появляется «Погашения рассрочки +X ₽»; оборот НЕ растёт.
4. У мастера «Касса сегодня» первый взнос рассрочки виден.

## Ограничения (честно)

- Погашения рассрочки — информационная строка, в оборот не входят (оборот по начислению —
  продуктовое решение этой волны).
- Битые `cash_card`-строки от старых (до-OTA) клиентов миграция не чинит (раскладка
  неоднозначна); класс перестаёт воспроизводиться серверной нормализацией — старые клиенты
  чинятся на сервере до раскатки обновления.
- dashboard-v2 кэшируется 30 с — после платежа цифра подтягивается в течение полуминуты.
