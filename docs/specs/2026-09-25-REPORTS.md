# Раздел «Отчёты» — конструктор отчётов (правка №3, 2026-09-25)

**Запрос владельца.** Раздел, где выбираешь, какой отчёт сформировать, за какой период и по
кому: по мастерам (все/выбранные — скидки, прибыль, чеки…), по поставщикам (купили /
заплатили / кто кому должен), по зарплатам (заработал / аванс / штраф / остаток или минус)
и ещё восемь отчётов, согласованных с владельцем: клиенты, товары, услуги, способы оплаты,
расходы, записи, филиалы, сводный.

Контракт зафиксирован в коде и первичен:

- `shared/types/index.ts` — секция «КОНСТРУКТОР ОТЧЁТОВ»: `ReportId`, `ReportResult`,
  `ReportColumn`, `ReportRow`, `ReportKpi`, `ReportSection`, `ReportQuery`,
  `ReportFilterOptions`, `ReportCatalogResponse`.
- `shared/reports/catalog.ts` — `REPORT_CATALOG` (названия, описания, методика, фильтры,
  права), `REPORT_MAX_DAYS`.
- `shared/api/createServices.ts` — `createReportBuilderApi` (`catalog`, `filterOptions`, `run`).

Идея: сервер отдаёт ЕДИНУЮ структуру (KPI + таблица + итого + секции + оговорки), клиенты
рендерят её одним универсальным экраном и одним экспортом. Новый отчёт = SQL на сервере +
строка в каталоге.

## 1. Backend — `backend/src/reports/builder/`

Новые файлы, чтобы не пересекаться с параллельной правкой `reports.service.ts` (воронка):

- `report-builder.controller.ts` — `@Controller('reports/builder')`; literal-маршруты
  `catalog` и `filters/:kind` объявлены ДО `:reportId`.
- `report-builder.service.ts` — диспетчер: валидация периода (`dateFrom ≤ dateTo`,
  ≤ 366 дней, иначе 400), проверка доступности отчёта (права/owner/филиалы → 403 с текстом
  из `reason`), кэш 30 с в памяти по `tenant+user+point+reportId+params`, вызов билдера.
- `builders/<reportId>.builder.ts` — по файлу на отчёт, общий интерфейс
  `build(ctx: ReportContext, query): Promise<ReportResult>`; `ctx` = tenantId, pointId,
  timezone, actor (роль/права), названия компании и филиала.
- `report-builder.module.ts` — регистрируется в `reports.module.ts` (единственная правка
  в существующих файлах модуля отчётов, кроме `app.module.ts`, если нужно).
- Доступ в раздел: право `financial_reports` (как у `/reports/financial`) **или** право
  конкретного отчёта из каталога (`salary_view`, `suppliers_access`, `clients_view`,
  `warehouse_access`, `bookings_access`) — чтобы завскладом мог открыть «По товарам», не имея
  финансовых прав. Owner-class байпасит всё. `points` — только owner-class и только при ≥ 2
  филиалах (`tenant_points`).
- Каталог доступности `GET /reports/builder/catalog` считает `available/reason` по тем же
  правилам.
- Фильтры `GET /reports/builder/filters/:kind`:
  `masters` — сотрудники с ролью мастер + все, у кого есть чеки как у мастера за последние
  12 месяцев (уволенные — с `sublabel: 'уволен'`), `employees` — все сотрудники тенанта, включая
  уволенных, `suppliers` — справочник поставщиков, `points` — филиалы тенанта.
  В скоупе филиала — сотрудники филиала (`user_points`) + те, у кого чеки в этом филиале.

### Общие правила расчёта

- Всё считается в поясе тенанта (`getTenantTimezone`, границы суток как в cashflow).
- «Проведённые чеки» и деньги — ТОЛЬКО через существующие формулы `common/*`
  (`checkRevenueExpr`, `checkMoneyBaseWhere`, логика возвратов/гарантии/рассрочки из
  `dashboardV2` и `getCashFlow`). Ни одной новой трактовки денег: цифры сводного отчёта за
  месяц обязаны совпасть с «Финансовым отчётом» и с «Движением денег» за тот же месяц —
  это acceptance-критерий.
- Скоуп филиала: чеки, расходы, зарплата, записи, склад — `pointFilterSql` по текущему
  филиалу сессии (как соседние эндпоинты); клиенты и поставщики — общие для сети (см.
  `docs/ios-redesign/POINT_WAREHOUSE_STAFF_2026-09-14.md`). Отчёт `points` — единственный,
  кто группирует по `point_id` поверх всего тенанта.
- Основная таблица ≤ 500 строк (`meta.truncated`, `meta.rowLimit`), секции ≤ 100 строк.
- Деньги — числа в рублях с копейками; проценты — числа 0–100; даты — `YYYY-MM-DD`.
- `notes` — оговорки методики словами владельца (см. `method` в каталоге), без жаргона.
- Каждый билдер — один-три SQL, без N+1.

### Состав отчётов (колонки основной таблицы, KPI, секции)

**summary — Сводный отчёт.**
KPI: выручка, себестоимость товаров, валовая прибыль, расходы (без зарплаты), зарплата
начислено, зарплата выплачено, прибыль после расходов (= валовая − расходы без ЗП − ЗП
начислено), чеков, средний чек, новых клиентов, возвраты, нам должны (долги клиентов +
остаток рассрочек), мы должны поставщикам. У выручки/прибыли/чеков/среднего чека —
`deltaPercent` к предыдущему периоду той же длины.
Таблица: по дням (период ≤ 31 дня) или по неделям — дата/неделя, чеков, выручка, прибыль,
расходы. Секции: топ-5 мастеров (чеки, выручка, прибыль), топ-5 услуг (кол-во, выручка),
топ-5 товаров (кол-во, выручка, прибыль), способы оплаты (способ, сумма, доля).

**masters — По мастерам** (фильтр: мастера).
Колонки: мастер, чеков, клиентов, выручка, работы, товары, скидки, себестоимость товаров,
прибыль, средний чек, возвратов (шт), возвраты (₽), начислено ЗП. Итого. KPI: выручка,
прибыль, чеков, скидки. Чек относится к `master_id` чека; если у строк чека свои мастера —
использовать ту же привязку, что и зарплата (иначе цифры разойдутся с отчётом по зарплате).

**salary — По зарплатам** (фильтр: сотрудники).
Колонки: сотрудник, начислено за работы, начислено за товары, премии и мотивация,
начислено всего, штрафы, авансы, выплачено ЗП, выплачено всего, остаток (`signed`; = начислено
всего − штрафы − выплачено всего; минус = переплата), смен, средний за смену. Итого. KPI:
начислено, выплачено, штрафы, остаток. Начисления — через `SalaryService` (тот же расчёт,
что видит мастер на своём экране — не переписывать формулу процента). Выплаты/авансы/премии/
штрафы — из `salary_payouts` / `salary_premiums` / `salary_penalties` по дате в периоде.
Секция: «Выплаты и удержания за период» — дата, сотрудник, тип (зарплата/аванс/премия/штраф),
сумма, комментарий.

**suppliers — По поставщикам** (фильтр: поставщики).
Колонки: поставщик, долг на начало (`signed`), поставок (шт), поставки (₽), оплаты (₽),
возвраты поставщику (₽), долг на конец (`signed`). Итого. KPI: поставки, оплаты, долг на
конец, поставщиков с долгом. Сальдо считать из журналов (`deliveries`, `supplier_payments`,
возвраты/сторно), а не из `suppliers.current_debt`; sanity-проверка: при `dateTo = сегодня`
долг на конец должен совпасть с `current_debt` (написать тестовый SQL на локальной базе и
описать расхождения, если есть). Секции: «Поставки за период» (дата, поставщик, сумма,
комментарий/документ), «Оплаты за период».

**clients — По клиентам.**
KPI: обслужено клиентов, новых, повторных, выручка от новых, выручка от повторных, средний
чек, давно не приезжали, долг клиентов. Таблица: топ клиентов по выручке — клиент (`_href`
`/clients/:id`), телефон, визитов, выручка, последний визит. Секции: «Давно не приезжали»
(последний визит > 90 дней; клиент, телефон, последний визит, дней назад, выручка за всё
время; сортировка по выручке), «Должники» (клиент, телефон, долг, просрочено по рассрочке).
Новый = первый чек клиента в периоде.

**products — По товарам** (`groupBy`: `product` | `category`).
Колонки: товар (или папка), папка, продано (шт), выручка, себестоимость, прибыль, наценка %,
остаток сейчас. Итого. KPI: выручка товаров, прибыль, средняя наценка, списано (₽), стоимость
залежавшегося товара (по себестоимости). Секции: «Залежались» (остаток > 0, продаж в периоде
нет: товар, остаток, стоимость остатка, последняя продажа, дней без продаж), «Списания и брак»
(дата, товар, кол-во, сумма, причина/тип — из движений склада за период).

**services — По услугам.**
Колонки: услуга, количество, выручка, средняя цена, доля %, чеков, мастеров выполняло. Итого.
KPI: выручка по работам, работ выполнено, разных услуг, средняя цена.

**payments — По способам оплаты.**
Колонки: способ (Наличные, Карта, СБП/эквайринг если есть, Рассрочка — первый взнос,
Рассрочка — платежи по графику, Гарантия — справочно), чеков, сумма, доля %. Смешанная
оплата раскладывается по частям. Итого (без гарантии). KPI: получено всего, наличные, карта,
выдано в рассрочку (долг), гарантия (справочно). Секция: «По дням» (дата, наличные, карта,
прочее, итого) при периоде ≤ 62 дней, иначе по неделям. Числа обязаны совпадать с
«Движением денег».

**expenses — По расходам.**
Колонки: категория, расходов (шт), сумма, доля от расходов %, доля от выручки %. Итого. KPI:
расходы всего, выручка, из них зарплата, расходы/выручка %. Секция: «Крупнейшие расходы»
(дата, категория, сумма, комментарий, сотрудник) — топ-20.

**bookings — По записям.**
KPI: записей, приехали (arrived + converted), оформлен чек (converted), не пришли (no_show),
отменены, конверсия в чек % (от всех, кроме отменённых), не пришли %, выручка по записям.
Таблица: по мастерам/постам, если у записи есть исполнитель, иначе по дням недели — записей,
приехали, не пришли, конверсия %. Секция: «Не пришли» (дата, клиент, телефон, услуга) —
для обзвона, топ-100.

**points — По филиалам** (фильтр: филиалы; owner-class; ≥ 2 филиалов).
Колонки: филиал, чеков, клиентов, выручка, прибыль, расходы, зарплата начислено, средний
чек, прибыль после расходов. Итого. KPI: выручка сети, лучший филиал по выручке, лучший по
среднему чеку.

### Проверки backend

`typecheck` + `lint` + `build`; каждый билдер прогнан на локальной базе `autexa-pg`
(данных мало — заполнить тестовыми через API или SQL, минимум: 3 мастера, 10 чеков с
разными способами оплаты и скидками, 2 поставщика с поставками/оплатами, авансы/штрафы,
расходы, 3 записи разных статусов); сверка сводного отчёта с `/reports/financial` и
`/reports/cashflow` за тот же период — совпадает до копейки.

## 2. Клиенты — универсальный экран

Общее для web и mobile:

- **Хаб «Отчёты»**: карточки из `REPORT_CATALOG` (только `available` из `catalog`),
  сгруппированные по `group`; недоступные — не показывать (или серым с `reason`, если это
  owner). Существующий «Финансовый отчёт» остаётся отдельным пунктом хаба («Финансовый
  отчёт — подробно») и открывается как раньше: ничего не теряем.
- **Экран отчёта**: пресеты периода (сегодня / вчера / неделя / месяц / квартал / год /
  произвольный — как в существующем `ReportsScreen`), сущностный фильтр (мультивыбор с
  поиском; чипы выбранных; «Все» по умолчанию), `groupBy` сегментами, кнопка «Сформировать»
  (и авто-запуск при смене пресета). Результат: KPI-плитки (`tone`, `deltaPercent` стрелкой),
  основная таблица (числовые колонки справа, `signed` — красный/зелёный, `_tone` строки,
  сортировка по клику на заголовок, итого закреплено), секции, «Методика» (`method` из
  каталога + `notes`), подпись «Сформирован … · филиал …». Пустой результат — понятный
  empty-state («За период нет проведённых чеков»). Ошибки 400/403 — текст сервера.
- **Экспорт**: web — Excel (`xlsx`: шапка компания/отчёт/период/фильтры, KPI, таблица с
  итого, секции; числовые форматы) и PDF (печатная HTML-версия → `html2pdf`, A4 альбомная
  для широких таблиц, тот же порядок); mobile — PDF через `expo-print` (шаблон в духе
  `orderPdf.ts`) + `expo-sharing`. Один универсальный генератор из `ReportResult`.
- **Права**: раздел виден при `financial_reports` ИЛИ любом доступном отчёте; сервер —
  источник истины (`catalog`).

**mobile** (агент M2): новые экраны `ReportsHubScreen` и `ReportRunScreen` в `MoreStack`;
маршрут `Reports` теперь ведёт в хаб; старый `ReportsScreen` → маршрут `FinancialReport`.
Таблица — горизонтальный скролл с закреплённой первой колонкой, 60 fps, persistent cache
для `catalog`.

**web** (агент фазы B): `ReportsPage` → хаб; `/reports/:reportId` → экран отчёта;
`/reports/financial` → старая страница. Строится на новой дизайн-системе
(`docs/web-redesign/DESIGN_SYSTEM.md`).
