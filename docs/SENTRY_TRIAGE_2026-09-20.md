# Разбор Sentry, 2026-09-20

Организация `web-kultura`, проекты `autexa-backend` (node-nestjs) и `react-native`.
10 незакрытых issue. Ниже — корневые причины по коду; каждая прошла состязательную проверку,
8 первоначальных версий отклонены как недоказанные или с неверным патчем.

Веб-фронт в Sentry **не пишет вообще** (`@sentry/*` только в `backend/` и `mobile/`), поэтому падение
autexa.pw к этим событиям отношения не имеет — см. `SITE_CRASH_OLD_SAFARI_2026-09-20.md`.

## 1. Корзина товаров: тихая потеря складской истории — САМОЕ СЕРЬЁЗНОЕ

**Issue:** `AUTEXA-BACKEND-S`, 2 события, 23 авг, `DELETE /api/products/trash/empty`.
Видимая ошибка — FK-нарушение `purchase_order_items_product_id_fkey`. Но она здесь не главная.

Полный перечень внешних ключей на `products(id)` — 9 штук:

| Таблица                     | ON DELETE                        | Что это значит                   |
| --------------------------- | -------------------------------- | -------------------------------- |
| `stock_movements`           | **CASCADE** (`001_init.sql:220`) | **складские документы**          |
| `price_history`             | **CASCADE** (`014:4`)            | история цен                      |
| `product_commissions`       | **CASCADE** (`009:19`)           | проценты                         |
| `motivation_promo_products` | **CASCADE** (`095:41`)           | акции мотивации                  |
| `check_product_lines`       | SET NULL                         | строки чеков                     |
| `delivery_items`            | SET NULL                         | строки поставок                  |
| `warranty_claims`           | SET NULL                         | гарантийные                      |
| `motivation_accruals`       | SET NULL                         | начисления                       |
| `purchase_order_items`      | **NO ACTION** (`084:59`)         | ← единственный, который ругается |

`stock_movements` — это не метаданные товара, это **реестр складских документов**:
`journal.service.ts:96-112` строит из него «Журнал → Документы склада», из него же считаются
стоимость склада и маржа. Записи туда попадают только от реальных операций — поставка,
инвентаризация, перемещение, возврат.

Значит: **каждое успешное удаление товара из корзины молча стирает все его складские документы
и историю цен.** Это происходит с момента миграции `023_soft_delete_products_categories.sql`,
не оставляет следов и не порождает событий в Sentry — потому что это успешный HTTP 200.

Парадокс: ошибка `purchase_order_items` — единственное, что **защищало** реестр у тех тенантов,
которые пользуются заказами поставщикам. Там, где заказов не было, данные уходили молча.

**Что НЕ надо делать:** менять CASCADE на SET NULL миграцией. `journal.service.ts:105` делает
`JOIN products p ON p.id = sm.product_id` — INNER. Движение с `product_id = NULL` исчезнет из
журнала ровно так же, только теперь ещё и незаметнее.

**Что надо:** не удалять физически товар, у которого есть хоть одна запись в `stock_movements`
(и в `purchase_order_items`). Разделить ссылки на жёсткие (история — держим товар) и мягкие
(можно обнулить), а в ответ эндпоинта вернуть, что удалено и что оставлено с причиной.
Слой — только сервисный SQL, миграция не нужна.

**Побочно:** у `check_return_lines.product_id` (`040_returns_and_defect.sql:25`) внешнего ключа нет
вообще — после физического удаления там остаётся висячий id.

## 2. `function min(uuid) does not exist` — УЖЕ ИСПРАВЛЕНО

**Issue:** `AUTEXA-BACKEND-T`, 46 событий, 11–13 сентября, `POST /api/schedule`.

В PostgreSQL 16 нет агрегатов `min`/`max` для типа `uuid`. Сломанный SQL появился в `96ab966`
(11 сент) и убран в `6b4a6f5` (13 сент) — даты совпадают с последним событием. Комментарий
в `schedule.service.ts:371`, упоминающий `MIN(tp.id)`, описывает прежний подход, а не текущий код.

Что при этом происходило у людей: отметка «пришёл/опоздал» падала с 500 **уже после** того, как
день сохранился. Клиент откатывал отметку, владелец видел «не сохранилось», а после обновления
отметка появлялась. Отсюда жалоба «расписание перестало работать».

Сплошная проверка всего бэкенда (264 совпадения `min(`/`max(`, каждое сверено с типом колонки
по миграциям) — **других агрегатов по uuid не осталось**. Три места, где uuid всё-таки агрегируется,
уже используют обход: `max(x.point_id::text)::uuid` (`162:226,258`), `MIN(...::text)::uuid` (`159:79,109`),
`(array_agg(x.point_id))[1] ... HAVING count(*) = 1` (`167:67-82`) — все корректны для PG16.

Делать нечего. При желании — грепающая проверка в CI на `(MIN|MAX)\s*\(\s*\w*id\b` без соседнего `::text`.

## 3. `PATCH /api/schedule/temp-…` — клиентский баг, жив

**Issue:** `AUTEXA-BACKEND-V`, 1 событие, 18 сентября.

`mobile/src/screens/ScheduleScreen.tsx:946-967` (`applyOptimistic`) пишет в кэш синтетическую строку
с `id: temp-${userId}-${date}`. Создание на строке 1100 **отбрасывает ответ сервера** — сверка
делегирована неотслеживаемому `invalidate`. Если следующее действие успевает раньше, плейсхолдер
всё ещё в кэше, и ветка «есть id → PATCH» отправляет `temp-…` как идентификатор.

Что видит владелец: отметка прихода отскакивает назад, вибрация ошибки, «Не удалось сохранить».
Симптом неотличим от того, что чинили в `6b4a6f5`. День при этом на сервере сохранён.

**Фикс — мобилка, один файл:** брать id из ответа `create` и заменять плейсхолдер через
`setQueryData` до `invalidate`; плюс страховка — не слать PATCH, если id начинается с `temp-`.

**Отдельно, бэкенд:** ни в одном из 34 контроллеров нет `ParseUUIDPipe` — 164 параметра `@Param('id')`
уходят в SQL без проверки. Кривой id возвращается как 500 с текстом ошибки Postgres вместо честного 400.
Это отдельная правка в закрытой зоне и делать её стоит **после** клиентской, чтобы смена статуса
не совпала с потоком кривых запросов.

## 4. `auth_expired_forced_logout` — 229 событий, 15 человек — ПРИЧИНА НЕ УСТАНОВЛЕНА

**Issue:** `REACT-NATIVE-1`, первое 4 июня, последнее сегодня.

Две рабочие гипотезы проверены и **отклонены**:

- _«Транспортный сбой выдаёт себя за протухшую сессию»_ — не подтвердилась. `status 0` физически не
  может дойти до ветки 401: она требует `error.response` и отсекается раньше, на `if (!error.response)`
  (`axios.ts:1327`). Все четыре хоста кольца фронтят один и тот же NestJS с одним `JWT_SECRET`,
  а 401 в том событии пришёл с прямого IP VDS — то есть от самой авторитетной инстанции.
- _«Виновата семидневная тихая ротация токена»_ — не подтвердилась по датам. Ротация появилась
  3 августа, а issue живёт с 4 июня. По тегам релизов: **37 из 38 событий — со сборок до 3 августа**,
  где этого кода в принципе не было. И форма не та: у одного пользователя **четыре разлогина за 78 секунд**,
  а механизм, срабатывающий раз в 7 дней на установку, такого дать не может.

Скорее всего, значительная часть этих 229 — **законные разлогины**: истечение 30-дневного токена,
смена пароля (`sessions_valid_from`), увольнение, деактивация, отзыв доступа к филиалу, выход на другом
устройстве. Каждая такая причина в `jwt.strategy.ts` своя и осмысленная.

**Почему нельзя сказать точнее.** `mobile/src/sentry.ts:141` шлёт
`captureMessage('auth_expired_forced_logout', 'warning')` **без extras**, а слушатель на строке 139
**выбрасывает аргумент `reason`**, который `axios.ts:1375` честно вычислил. Три с половиной месяца
событий физически не могут назвать, какая из причин сработала.

**Рекомендация: сначала приборы, потом патч.** Донести `reason` (и хост, и код статуса) в событие —
это одна строка в `sentry.ts`. После следующего релиза неделя данных ответит на вопрос, который
сейчас не берётся никаким чтением кода.

Попутно найдены две **настоящие** узкие дыры (реальные, но volume не объясняют):

- ветка 401 не исключает `htmlErrorResponse` (`axios.ts:1249`), хотя везде в файле он учитывается:
  401 с HTML-телом от промежуточного узла оператора убивает живую сессию;
- `POST /auth/refresh` (`AuthContext.tsx:841`) — обычный авторизованный POST без
  `beginSessionReissueWindow` и без single-flight, одна попытка с пустым `catch {}`. Сервер при
  ротации отзывает старый токен **до** выдачи нового (`auth.service.ts:388-407`), поэтому потерянный
  ответ убивает сессию навсегда. Комментарий на `AuthContext.tsx:855-856` утверждает обратное — он неверен.

## 5. 401 при регистрации push-токена — шум

**Issues:** `REACT-NATIVE-5` (71 событие) + `AUTEXA-BACKEND-P` (14 предупреждений).

`registerPushToken` (`mobile/src/contexts/AuthContext.tsx:589-679`) запускается «выстрелил и забыл»
из `prefetchAfterLogin` и имеет лестницу ретраев до ~35 с, но **ни разу не перепроверяет сессию**
между стартом и `pushApi.register` на строке 641. Если сессия за это время кончилась, POST уходит
без неё, ловит 401 и отправляется в Sentry как исключение приложения.

Прямого вреда нет, но эти 71 событие три с половиной месяца маскировали историю с разлогинами.
Фикс — мобилка, одна функция: проверять сессию перед отправкой и трактовать 401 здесь как
«сессия кончилась», а не как ошибку.

## 6. Зависания и убийство по памяти — данных мало

**Issues:** `REACT-NATIVE-C` (WatchdogTermination, 5 событий, 1 человек), `REACT-NATIVE-H`/`G`
(App Hanging ≥ 2 с, по 1 событию, оба 18 сентября 13:43).

Оба зависания — работа главного потока UIKit/CoreAnimation, а не JS-подозреваемые (разбор JSON,
AsyncStorage). React-кадры **не символизированы**: в `mobile/app.json` не настроен build-плагин Sentry,
поэтому вместо имени функции приходит `<redacted>`.

Гипотеза про `/api/products?limit=10000` как причину watchdog'а **проверена и отклонена** — по таймлайну
не сходится. При этом сам двойной запрос каталога на холодном старте — реальная находка, просто
к этому событию отношения не имеет.

Честно: 5 событий с одного устройства — это не основание для правок вслепую. Сначала символизация
(плагин в `app.json` + `SENTRY_AUTH_TOKEN` в секретах EAS, затем обязательный `expo prebuild --clean`

- `pod install` + новый buildNumber), потом смотреть.
