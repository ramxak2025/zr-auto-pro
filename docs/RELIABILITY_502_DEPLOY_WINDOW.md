# Надёжность: «Не удалось загрузить / повторить не помогает» — корень и фикс

**Дата:** 2026-06-18
**Ветка фикса (клиент):** `fix/reliability-deploy-window` (коммит `af1efa8`)
**Статус:** клиентский фикс — реализован, отревьюен, в TestFlight (build 20). Серверный (инфра) фикс — спроектирован, ждёт решения владельца (риск авто-деплоя).

---

## 1. Симптом

На iOS периодически во многих разделах сразу: «Не удалось загрузить … Повторить», и «Повторить» не помогает — тот же результат. Лечилось «само» через некоторое время.

## 2. Корень (подтверждено данными, не догадка)

Два независимых корня, складывающихся в симптом:

### A. Сервер создаёт 502-окно на каждом деплое (истинный источник)

- `deploy.sh:103` → `docker compose up -d --no-deps --force-recreate backend frontend`. Единственный backend-контейнер уничтожается без перекрытия; новый не вызывает `app.listen()` пока NestJS не прогонит `onModuleInit` (migration-runner, 73 файла) → нет слушателя на :3000.
- `frontend/nginx.conf` — статический `upstream backend_pool { server backend:3000 }` без `resolver` и без `proxy_next_upstream`: nginx кэширует старый IP, единственный ответ на мёртвый upstream — 502.
- Реальное пользовательское 502-окно: **~6–12с** на чистом деплое, **15–30с+** на тяжёлой миграции / при нехватке диска.
- Sentry подтверждает: **REACT-NATIVE-5 «status code 502» — 48 событий, 6 пользователей, последнее сегодня**; 504/«нет соединения» — единичные.

### B. Клиент сдавался быстрее, чем длится окно, и не восстанавливался сам

- Транзиентный ретрай в `App.tsx`: 2 попытки, задержки 500мс+1000мс = **~1.5с** покрытия. 1.5с ≪ 15с → запрос падал в terminal `error`, «Повторить» внутри того же окна снова ловил 502.
- 502 — **не оффлайн** (сокет жив): `onlineManager`/`refetchOnReconnect` никогда не срабатывают → запрос навсегда в `error` до ручного ретрая. Единственный авто-хил — `refetchInterval:30000` на 3 экранах (узко, 30с).

## 3. Клиентский фикс (реализован, в build 20)

Цель — приложение топового уровня надёжности: невидимо переживать 502-окно и авто-восстанавливаться. Всё mobile-only (shared/ не тронут → web и Android-контракт целы), мутации не тронуты (нет риска двойных списаний).

| Изменение                            | Файл                                          | Что делает                                                                                                                                                                                                                                                                            |
| ------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Расширенный транзиентный ретрай      | `mobile/src/utils/queryRetry.ts` (new)        | network/timeout/5xx ретраятся до 6 раз, capped backoff 8с + ±25% jitter (~31с покрытия) — переживает деплой невидимо. **4xx не ретраятся никогда** (детерминированы).                                                                                                                 |
| Авто-восстановление по /health       | `mobile/src/utils/backendRecovery.ts` (new)   | Пока есть active + транзиентно-errored запрос — поллит `GET /health` (2→4→8с); первый 200 → `refetch` только этих запросов (`type:active`, `cancelRefetch:false` — не сбивает идущий ретрай). Cooldown против спина, уважает onlineManager, **исключает 4xx**. Чинит без «Повторить». |
| Единая retry-политика + connectivity | `mobile/App.tsx`                              | Подключение по `isInternetReachable` (фолбэк `isConnected`, чтобы не мигало на cold-start).                                                                                                                                                                                           |
| ClientsScreen                        | `mobile/src/screens/ClientsScreen.tsx`        | Добавлен `error+retry` бранч (был вечный скелетон при cold-start ошибке без кэша).                                                                                                                                                                                                    |
| Cold-start фолбэк detail-экранов     | `mobile/src/utils/persistentCache.helpers.ts` | `supplier*`/`check`/`car-checks` теперь персистятся (+ VARIANT_CAPS), чтобы открытие карточки во время 502 не давало hard-error.                                                                                                                                                      |

**Проверки:** typecheck 0, lint 0, jest **261 зелёных** (+22 новых). Корень найден мульти-агентным анализом, дифф прошёл адверсариальное ревью (4 скептических линзы + release-gate); все найденные дефекты исправлены (транзиент-only гейтинг, `cancelRefetch:false`, `isActive()`).

## 4. Серверный (инфра) фикс — РЕКОМЕНДАЦИЯ, ждёт решения владельца

Истинный источник 502 — на сервере. Самый безопасный вариант, **НЕ повторяющий аварию с variable `proxy_pass`** (14-мин даунтайм /api):

1. `docker-compose.yml`: добавить второй идентичный backend-реплику `backend2` (та же сборка/env/healthcheck). Стоимость ~+150–250 МБ RAM — **нужно проверить запас на VDS**.
2. `frontend/nginx.conf`: апстрим оставить **статическим именованным** (`proxy_pass http://backend_pool/api/;` байт-в-байт без изменений), но:
   ```nginx
   upstream backend_pool {
       server backend:3000  max_fails=2 fail_timeout=5s;
       server backend2:3000 max_fails=2 fail_timeout=5s;
       keepalive 32;
   }
   ```
   и в `location /api/` + `location /api/imports/`:
   ```nginx
   proxy_next_upstream error timeout http_502 http_504;
   proxy_next_upstream_tries 2;
   proxy_next_upstream_timeout 6s;
   ```
   (только idempotent connect-time фейловер; `non_idempotent` НЕ добавлять — POST/PUT не ретраить.)
3. `deploy.sh`: rolling recreate — собрать, пересоздать `backend` → дождаться healthy → пересоздать `backend2` → дождаться healthy → последним `frontend`. В каждый момент ≥1 живой реплики; nginx обходит ту, что пересоздаётся → пользователь не видит 502.

**Почему не запушено сразу:** изменение авто-деплоится при push в `refactor/full-audit-2026`; прошлый непроверенный nginx-пуш уронил прод на 14 минут; без доступа к VDS нельзя прогнать `nginx -t` и проверить запас RAM под `backend2`. Клиентский фикс уже убирает симптом для пользователя, поэтому инфра-фикс применяем только с подтверждением владельца / валидацией на сервере. **Нельзя:** возвращать variable `proxy_pass` + `resolver`; убирать `--no-deps`; двигать миграции после `listen()`.

## 5. Чек-лист приёмки (владелец, на физическом iPhone)

- [ ] Во время деплоя (или сразу после) открыть Расписание/Журнал/Склад — данные показываются (из кэша) или появляются в течение ~несколько секунд **без** «Не удалось загрузить».
- [ ] Если карточка ошибки всё же появилась — она исчезает сама в течение ~10с после возврата бэкенда, без нажатия «Повторить».
- [ ] Клиенты: при холодном старте с ошибкой — карточка ошибки с рабочей кнопкой «Повторить», а не вечный скелетон.

## 6. ОБНОВЛЕНИЕ 2026-06-19 — подтверждённый 504 на создании чека

**Что случилось:** владелец прислал скриншот `504 Gateway Time-out (nginx/1.31.2)` ровно
на создании чека в Кассе. Это **окончательно** доказало: корень — на сервере (окно
деплоя), а НЕ на устройстве. Раньше я ошибочно свёл это к «проблема на телефоне» —
неверно.

**Почему именно 504, а не 502 (уточнённый механизм):**

- Рантайм-пул: `statement_timeout = 8s`, `connectionTimeoutMillis = 5s`
  (`backend/src/common/db-config.ts`). Значит один запрос физически НЕ может висеть
  60 с — он упал бы за ~5–13 с как 500. 60-секундный 504 = запрос **никогда не получил
  ответа**.
- `main.ts` НЕ вызывал `enableShutdownHooks()`. При `deploy.sh` →
  `--force-recreate backend` старый контейнер убивался **посреди запроса** (POST
  /checks «в полёте»), соединение рвалось, nginx (keepalive к умирающему апстриму)
  ждал `proxy_read_timeout 60s` → 504.
- «Товар 0 → ошибка»: ложная атрибуция. Клиент УЖЕ разрешает продажу в минус (мягкое
  «Не хватает на складе… Продолжить?», `CheckCreateScreen.tsx:1411`), а ошибка была
  тем же 504. Но бэкенд прибивал сток к 0 через `GREATEST(stock-$1,0)` — владелец
  просил именно «в минус».

### Tier 1 — РЕАЛИЗОВАНО и проверено (низкий риск, без nginx)

| Изменение                                                                                                    | Файл                                   | Эффект                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app.enableShutdownHooks()` перед `listen()`                                                                 | `backend/src/main.ts`                  | На SIGTERM Nest корректно сливает запросы «в полёте» до выхода → POST создания чека ДОзавершается и отдаёт 201, а не теряется в 504.                                              |
| `stop_grace_period: 30s` на backend                                                                          | `docker-compose.yml`                   | Docker ждёт слива до 30 с перед SIGKILL (дефолт был 10 с).                                                                                                                        |
| Сток уходит в МИНУС: `GREATEST(stock-$1,0)` → `stock-$1` (2 места: `create()` и `applyDeferredActivation()`) | `backend/src/checks/checks.service.ts` | «Продажа в минус» как просил владелец. Симметрично пути возврата (`stock+qty`) — отменённый оверселл восстанавливает сток ровно (раньше `GREATEST` давал латентный over-restore). |

**Проверки:** backend `typecheck` 0, `lint` 0 ошибок, `build` exit 0. Контракт API не
тронут (shared/ цел → web и Android не задеты). Новых миграций нет. Деплоится в одиночку
безопасно: чинит именно тот 504. **При деплое этого Tier 1 будет одно последнее окно**
(старый контейнер ещё без graceful shutdown), после него 504-на-деплое уходит.

### Tier 2 — ГОТОВ к применению, ГЕЙТ: проверка RAM на VDS

Полный zero-downtime (убирает и оставшееся 502-окно на новых POST во время загрузки
нового контейнера). НЕ закоммичен в авто-деплой-ветку, потому что nginx-апстрим начнёт
ссылаться на `backend2` — если его не поднять, nginx не стартует (= /api ляжет). Поэтому
все 4 части применяются ТОЛЬКО ВМЕСТЕ и после подтверждения запаса RAM.

1. `docker-compose.yml`: backend получает `image: autexa-backend:latest`; добавить
   идентичный сервис `backend2` (тот же image, env, healthcheck, `stop_grace_period`,
   `RUN_BACKGROUND_JOBS: 'false'`). Стоимость ~+150–250 МБ RAM.
2. `frontend/nginx.conf`: апстрим **остаётся статически именованным** (НЕ variable
   `proxy_pass` — это уронило прод на 14 мин), добавляются второй `server backend2:3000`
   и `proxy_next_upstream error timeout http_502 http_504` + `_tries 2` + `_timeout 6s`
   в `location /api/` и `/api/imports/`. **Только idempotent-фейловер** —
   `non_idempotent` НЕ добавлять (POST/PUT не ретраить → нет двойных списаний).
3. `deploy.sh`: rolling recreate — поднять `backend2` → пересоздать `frontend` (новый
   nginx с фейловером) → пересоздать `backend` (ждать healthy) → пересоздать `backend2`
   (ждать healthy). В каждый момент ≥1 живой реплики.
4. Корректность при 2 репликах (ОБЯЗАТЕЛЬНО иначе двойные сайд-эффекты):
   - `migration-runner.ts`: обернуть прогон в `pg_advisory_lock` — две реплики не гонят
     миграции одновременно;
   - leader-флаг `RUN_BACKGROUND_JOBS` (default true; на `backend2` = false) гейтит ВСЕ
     фоновые джобы, чтобы они шли только на одной реплике:
     `booking-reminder` (setInterval), `marketing.service` (job+scan intervals),
     `marketing/reminder` (scheduler), `warehouse-analytics` (@Cron),
     `shifts/shift-auto-close` (@Cron), `auth` (@Cron). НЕ трогать
     `rate-limit.guard` setInterval — это per-process чистка памяти, должна идти на
     каждой реплике.

**Проверка перед Tier 2 (владелец, одна команда на VDS):** `free -h` — нужен запас
≥ ~300 МБ под `backend2`. Если запас есть — применяю Tier 2; если тесно — остаёмся на
Tier 1 (он уже убирает 504).
